# Changelog

## v2.4.0

- **Added:** AMQP heartbeat on every asynchronous connection — 30 s by default, overridable via Connection extra `heartbeat` (the same key `RMQHook` already reads, where the default stays 600 s); `"heartbeat": 0` is accepted as a deliberate opt-out and logged as a WARNING. Heartbeats are what turn a silently broken link into an exception `connect_robust` can react to: without them a broker restart behind a proxy that keeps the client half open left the consumer waiting forever on a connection the broker no longer knew about
- **Added:** Connection extras `connect_timeout` (default 15 s) and `rpc_timeout` (default 30 s) — timeouts for the watcher's asynchronous AMQP calls: connect, `channel()`, declare, bind, publish, including the provisioning branches inside the reconcile cycle
- **Added:** Liveness watchdog — every reconcile cycle asks the broker whether each subscription's own consumer tag `rmq_watcher.{hostname}.{pid}.{sub_id}.{nonce}` is still registered, reading `GET /api/consumers/{vhost}` or falling back to a passive `queue_declare` probe when the connection has no `management_url` (rationale in ADR-0007)
- **Added:** Two negative liveness checks in a row cancel exactly the subscriptions whose own tag the broker did not confirm, drop the connection they share and start fresh tasks; the confirmed subscriptions of that `conn_id` keep their own retry loop and are named in a WARNING, and the cooldown fire task goes down with the connection it holds for its whole life
- **Added:** A Management API failure counts as "no data": WARNING, counters untouched, stored status kept
- **Added:** A `conn_id` whose consumers the broker denies is written as `error` with the reason and the check number on the cycle that finds it — the two consecutive checks gate the restart, not the report
- **Added:** The same `conn_id` is recreated at most once every 5 reconcile cycles
- **Added:** Cycle timeout — one reconcile iteration runs under a budget of `max(reconcile_interval * 3, 300)` s, overridable via Airflow Variable `rmq_watcher_cycle_timeout`. Exceeding it logs the phase (`migrate`/`scan`/`sync`/`read subs`/`reconcile`) and its duration, then recreates the event loop. Every blocking step of a cycle — the DAG-file scan, the sync to the database and the subscription read — runs under a 60 s bound of its own and with a single attempt in flight, so a database that stopped answering ends the cycle instead of spending the whole budget and taking every consumer task down with the loop, and cannot fill the four-worker cycle pool with stuck copies of the same call
- **Added:** Status `degraded` — a negative liveness verdict that the connection-recreation rate limit held back; repeated occurrences mean the classification is wrong or the problem is not in the connection
- **Added:** A `conn_id` whose tasks are alive but never reach `listening` for two cycles in a row is asked directly whether it still answers an RPC — a passive `queue_declare` on a fresh channel of that pooled connection — because the check has no candidate to put to the broker. Silence recreates the connection: that is the shape of a pool whose `channel()` never returns, where every task retrying on it meets the same silence. An answer leaves it alone and says so in the row: tasks stuck in `error` because their trigger keeps failing are attached to a healthy connection, and dropping it would blame the broker for a metadata-database outage. A `conn_id` no check has ever reached a verdict on is reported as `unknown` rather than green
- **Added:** The consumer tag carries a per-attach nonce, so a ghost consumer the broker still holds after a `close()` that never returned cannot vouch for the task that replaced it
- **Added:** The liveness check falls back to the passive-declare probe after two Management API failures in a row on one `conn_id` — a wrong URL or credentials without the `management` tag must not disable the watchdog altogether — and one `GET /api/consumers/{vhost}` is shared by every `conn_id` pointing at the same broker and vhost within a cycle
- **Added:** Separate publishing connection per `conn_id` for cooldown publishing. Under a resource alarm RabbitMQ blocks a publishing connection by no longer reading from its socket, which takes down `basic.ack` of every consumer sharing it — and a connection the broker has flagged blocked stops writing on the client side too, since `aiormq` holds its own writer until `connection.unblocked` arrives; with publishing split off the block stays inside the publishing connection, and the consuming one, which publishes nothing, is never flagged. A connection opened *while* an alarm is on is a separate matter, covered by the client-side bound on connect below. Two publish timeouts in a row are its own liveness verdict and recreate it alone. A publish that keeps failing pauses the subscription for a growing interval (1 s, doubling up to 60 s, reset by the next successful publish) before reattaching: a resource alarm lasts as long as it lasts, and redelivering the requeued message every reconnect delay burns a quorum queue's delivery limit long before the alarm clears
- **Added:** Columns `broker_consumer_count` and `last_reconcile_at` in `rmq_watcher_conn_status`, created by an idempotent migration (`inspect` + `ALTER TABLE ... ADD COLUMN` for what is missing) that the watcher loop retries until it succeeds, one attempt in flight, waiting out a growing backoff of 1 to 60 cycles between attempts — a database unavailable at plugin load no longer leaves the process running against an outdated table
- **Added:** The Subscriptions page shows the broker's consumer count next to the watcher's and highlights a mismatch, shows the age of the last reconcile cycle per `conn_id` and flags it when it is older than two reconcile intervals, and renders a "schema not migrated yet" notice instead of crashing while the table is still behind
- **Added:** Blocking calls run in bounded thread pools of the watcher's own — one for consumer tasks, one for the reconcile cycle, never shared: a database stuck on consumer work must not starve the cycle that is supposed to notice and recover from it. A pool holds three calls per worker, running and waiting together, and refuses anything beyond that instead of queueing it: a cancelled call cannot be taken back out of a `ThreadPoolExecutor` queue, so an unbounded one turns a database outage into memory growth on every retry, message payloads included. A refused call is a requeued delivery or a status write left for the next attempt; saturation is logged rather than silently queued
- **Added:** The status of a subscription is written by a single writer of its own, one write at a time, for as long as the process lives. The caller waits 30 s for a write and the write itself carries on afterwards, so two of them could otherwise be in the pool at once and leave the row showing `listening` for a subscription whose state has since become `error` — with nothing to correct it, since the manager already counts the newer value as stored. A caller that finds the writer busy leaves its status behind and returns at once: the running write takes it, only the newest of the statuses left that way survives, and no write ever waits for another one on a worker of its own. The writer outlives the task, its state and the manager itself, all of which recovery replaces, because the row it owns does too
- **Added:** A cancelled consumer task that has not finished when the cycle stops waiting for it is kept until it does, rather than left to asyncio's weak reference alone; it lets go of itself the moment it finishes. Each such task is counted once, as it is abandoned, in `rmq_watcher.tasks_abandoned` and logged as a WARNING — a count that keeps growing means the connection they hang on answers nothing at all
- **Added:** Log lines the watcher was missing — an INFO on a successfully started thread, naming the built-in reconcile interval and cycle budget it starts on (the line runs before the first settings read), followed by a separate INFO once the first cycle has read the Variables and found an override, an INFO on every successful (re)connection with `conn_id` and queue name, and an explicit reason when `on_starting` does not recognise the Airflow component and leaves the watcher unstarted
- **Added:** Statsd metrics `rmq_watcher.consumer_attached`, `rmq_watcher.consumer_restarted`, `rmq_watcher.dag_triggered`, `rmq_watcher.cycle_timed_out`, `rmq_watcher.cycle_step_timed_out`, `rmq_watcher.cycle_step_skipped` and `rmq_watcher.tasks_abandoned` (no-ops when statsd is not configured)
- **Changed:** immediate mode (`cooldown=0`) is now at-least-once — a delivery is ACKed **after** `trigger_dag` created the DAG run, not before. A failed trigger is NACKed with requeue and retried with a growing backoff (1 s, doubling up to 60 s) while the subscription status becomes `error` with the reason. Redelivery is deduplicated by the deterministic run id `rmq__{queue}__{message_id}`, so deduplication trusts the producer: two different messages carrying the same `message_id` collapse into one DAG run, and without a `message_id` a redelivery starts the DAG again. A DAG that is paused, inactive or missing stays a terminal ACK — the event is dropped on purpose rather than turning a paused DAG into an accumulator of redeliveries
- **Changed:** `status` in `rmq_watcher_conn_status` follows the broker's verdict instead of the number of unfinished tasks: a `conn_id` with no verdict keeps whatever status is stored, one that has never had a verdict is written as `unknown`, and the number of tasks the watcher started never makes a row green. A row is written for every `conn_id` present in the subscription list, with its counts and `last_reconcile_at` stamped every cycle — a `conn_id` whose tasks all died used to freeze on its last value, which is how a dead connection kept showing `connected` for a day
- **Changed:** the `conn_id` that carries the cooldown fire consumer is chosen as the smallest of the cooldown subscriptions' `conn_id`s instead of the first row the query returned. That query has no `ORDER BY` and PostgreSQL reorders rows an `UPDATE` touched — which every consumer-status transition does — so the fire consumer used to move, and be cancelled and restarted, during exactly the reconnect turbulence cooldown has to survive. Cooldown subscriptions spread over more than one `conn_id` are now logged as an ERROR naming them: the pending queues exist only on the chosen broker, while a matched delivery is published to the pending queue of its own connection
- **Changed:** a cooldown placeholder the broker rejects is acknowledged as terminal instead of being requeued — the pending queue is declared `x-max-length=1` with `x-overflow=reject-publish`, so a rejection is the ordinary answer while a cooldown window is already open and a second placeholder would add nothing; requeueing it would redeliver the same message for the whole window and burn the quorum-queue delivery limit on it
- **Changed:** `before_stopping` wakes the reconcile loop immediately instead of letting it sit out the rest of the interval, and joins the thread with a 5 s timeout; `manager.stop()` during loop teardown runs under a timeout of its own so a manager that cannot finish does not block the fresh loop
- **Fixed:** the timeout around an AMQP call is now a bound on the caller alone. A call that has not returned in time is cancelled and left to finish on its own, where before the caller waited for the cancellation to complete: an `aiormq` RPC answers a cancellation by closing its channel, and the close writes a frame to the very socket the call is stuck on, so `basic.consume` and `basic.cancel` on a silent broker stayed pending well past their timeout — the two calls the consumer's recovery paths depend on
- **Fixed:** a cooldown placeholder that reached no queue at all silently dropped the event. The publish channel is opened with `on_return_raises=True`: an unroutable `mandatory` publish comes back as `basic.return` followed by an ack, which on aio_pika's default channel resolves the publish *successfully* and hands the returned message back as its result — so the missing pending queue looked like a normal publish and the delivery behind it was acknowledged. The delivery is now requeued and the queue is declared again on the next reconcile cycle
- **Fixed:** `listening` and the consumer tag were published before `basic.consume` was confirmed, and the registration had no timeout of its own. A registration that hung left the liveness check vouching for a tag the broker never held — a connection reading `connected` with nothing consuming. The registration is now bounded by `rpc_timeout` and the status follows the broker's confirmation
- **Fixed:** a fire-queue delivery whose DAG trigger failed was left neither acknowledged nor requeued, and sat unacknowledged on the abandoned channel until the broker's `consumer_timeout`; it is now NACKed with requeue, as the immediate path already did
- **Fixed:** a fire event whose trigger kept failing came back every reconnect delay (5 s), which spends the default delivery limit of a quorum queue in about a hundred seconds — and `rmq_watcher.fire` is declared with no dead-letter exchange, so the cooldown DAG run the event stood for was silently lost. The fire path now waits out the same growing pause as the immediate one (1 s, doubling up to 60 s, reset by the next success) and reports the failure as its own status instead of unwinding the consumer on every failed trigger
- **Fixed:** consumer and fire channels were never closed when the iterator exited — aio_pika only cancels the consumer — so every failed publish or trigger left one more open channel on the connection. The channel of each attach is now closed on the way out, and cancelling the consumer is bounded (`basic.cancel` is an RPC a zombie connection never answers, and aio_pika awaits it without a bound)
- **Fixed:** the watcher's own timeout now bounds the whole connect. `connect_robust(timeout=…)` covers the TCP connect and the AMQP handshake and stops there; the wait that follows — for the broker to declare the connection unblocked, which under a resource alarm lasts as long as the alarm — is outside it, so a connect made during an alarm never came back. Awaited under one manager-wide lock, that single connect stalled connection creation for every `conn_id`, the reconcile cycle's own probes included; the cycle then died on its budget before writing any status row, and the row kept reading `connected` with nothing consuming — the incident's own signature
- **Fixed:** a consumer task cancelled while connecting left a live connection to the broker in no pool at all: `RobustConnection` runs the connect in a task of its own, so the assignment into the pool never happened while the connection factory went on reconnecting it. Cancellation is routine here — recovery, any subscription edit and `stop()` all do it — so the connection object is now pooled before it is connected, and `_drop_connection` and `stop()` close it along with the connect it was waiting for. A connect that runs out of time is left in flight rather than cancelled (cancelling the wait cancels the future the connection factory resolves, after which every later `connect()` of that connection raises at once) and the next caller waits on that same attempt instead of opening a second connection; a connect that *failed* takes its connection with it, because the object answers every later `connect()` with the same failure
- **Changed:** connections are built under a lock of their own `conn_id` instead of one lock for the whole manager, and the Airflow-connection read that precedes it happens outside that lock. Behind the shared lock the cycle's probes queued after every consumer task of every `conn_id`, and the wait grew as N × `connect_timeout` — about twenty subscriptions on one unreachable broker were enough to exhaust the cycle's budget, and exceeding it tears down the manager and cancels the tasks of every `conn_id`, healthy brokers included
- **Fixed:** a status write the caller stopped waiting for left the manager's marker and the row disagreeing for good. The abandoned worker commits that status once the database recovers, while the caller kept its own idea of what was stored, and the guard that skips an unchanged status then suppressed every write that could correct it — a subscription reading `listening` while every trigger it makes fails. The marker now lives with the writer that commits it and moves only on a committed write
- **Changed:** a subscription that cannot attach reports `error` with the reason instead of staying `connecting` — a `basic.consume` the broker never confirms left the row looking like a task that is merely starting up — and a `last_error` is never empty: an exception with no message of its own is reported by its type
- **Fixed:** a redelivered message was classified as a trigger error rather than a duplicate — Airflow 2.9+ raises `DagRunAlreadyExists` from `trigger_dag` before the INSERT, and it is not a subclass of the `IntegrityError` the code caught
- **Fixed:** `trigger_dag` is now called with `replace_microseconds=False`. With microseconds zeroed, `DagRun.find_duplicate` matches on `execution_date` as well as `run_id`, so two distinct messages arriving within the same second looked like a redelivery of each other and a burst produced a single DAG run
- **Fixed:** `RMQTrigger` in push mode acknowledged the message before decoding its body, so a non-UTF-8 payload raised `UnicodeDecodeError` on an already-acknowledged event and lost it — the body is decoded with `errors="replace"`, as everywhere else
- **Fixed:** a normal exit from the queue iterator (the broker cancelling the consumer) restarted the subscription with no delay, spinning the loop; there is now a pause before resubscribing
- **Fixed:** a connection whose reconnect never finished was handed out of the pool for as long as the process ran. aio_pika's reconnect factory clears the transport before each attempt it makes, so such an object reports `is_closed` False with nothing under it and answers every `channel()` with `RuntimeError("Connection was not opened")`; the pool asked only whether it was closed, so a consumer task failed on it, paused five seconds and was handed the same object again. Observed in production for two and a half days after a broker restart, ending only with a container restart. Being pooled, unclosed and usable are now three different questions, and a connect still in flight keeps its connection — that object is what every waiter is waiting on
- **Fixed:** the fire consumer started on whichever object the pool held, without asking whether it was connected. A connection is pooled from the moment its connect starts and reports `is_closed` False until it is closed, so a failed provisioning left the fire task running against an object with no transport, failing every call and kept alive by its own retry loop — and therefore out of every restart path, leaving `rmq_watcher.fire` without a consumer for good while the `conn_id` read `connected`. It now starts only on a connection that answers, and a task left on an object the pool has replaced is restarted rather than left spinning on the failure that object holds
- **Fixed:** a cancelled consumer task could survive its own cancellation and go on consuming with nothing holding it. aio_pika cancels the consumer from inside `QueueIterator.__anext__` while it handles the `CancelledError`, waits for that cancel without a bound and catches only a timeout of it, so a broker that rejects the pending `basic.cancel` — which every connection torn down mid-call does — let its own error out in place of the cancellation. The retry loop read that as a transient fault and subscribed again: reconcile could not cancel the resulting task, `stop()` could not see it, and it wrote status into the row its replacement owned, triggering the DAG of a removed subscription or running the old filter beside the new one
- **Fixed:** callers of one `conn_id` waited for the same connect one behind another, each paying the full `connect_timeout`, because the lock was held across the wait. The attempt behind that wait does not end on its own: a connect that times out raises `asyncio.TimeoutError`, which is not one of aio_pika's `CONNECTION_EXCEPTIONS` on Python 3.10, so its reconnect factory logs it, sleeps and tries again while `connect()` waits on a fail-fast future nothing resolves. With every subscription of a deployment usually on one `conn_id`, twenty of them gave the reconcile cycle a queue of 20 × 15 s — the whole default cycle budget — and a cycle that runs out of budget tears the manager down and cancels the consumer tasks of every healthy broker with it. The lock now covers starting the attempt, and the callers wait for it side by side
- **Fixed:** a status write that failed took its status with it, and a subscription that reached its steady state and then went quiet makes no further write to carry it — a database outage during the transition to `listening` left the row saying `connecting` for as long as the task ran. The failed status goes back to being the one to store next unless a newer one is already waiting, and the reconcile cycle stores whatever is left over
- **Fixed:** `inf` and `nan` passed both number parsers — `float()` reads them happily and neither is caught by a positivity or minimum check. An infinite cycle budget is a watchdog that never fires and an infinite `connect_timeout` a connect with no bound at all, which is what every bound here exists to provide; both parsers now require a finite value and fall back with a WARNING
- **Limitation:** `prefetch` is deliberately not set. Filter misses are NACKed with requeue and come back to the head of the queue, so any finite prefetch window eventually fills up with them and consumption stops for good — while the status still reads `connected`. The price is unbounded unacknowledged deliveries: a queue with a large backlog is read into scheduler memory, and the oldest delivery can hit the broker's `consumer_timeout` (30 minutes by default), after which RabbitMQ closes the channel with `PRECONDITION_FAILED` and returns the whole window. Raise `consumer_timeout` in the RabbitMQ configuration if large backlogs are expected

## v2.3.0

- **Added:** the Subscriptions page now marks with a `⚠ dag not found` badge any subscription whose `dag_id` doesn't correspond to any active Airflow DAG
- **Added:** `dag_id` in `@dag(...)` now resolves simple module-level string constants (`DAG_NAME = 'x'` → `dag_id=DAG_NAME`), including the positional form `@dag(DAG_NAME)` — not just string literals
- **Changed:** an unresolvable `dag_id` (not a literal and not a simple module-level constant — imported constants, f-strings, concatenation, function calls, `**kwargs` unpacking) no longer falls back to the function name. The subscription is now skipped entirely, with a WARNING logged instead. This removes not only previously-broken subscriptions: if a DAG's `dag_id` happened to statically fall back to a python function name that *coincided* with the real `dag_id` (e.g. `DAG_NAME = "my_dag"` imported from another module, and the decorated function literally named `def my_dag():`), that subscription worked correctly before this change and will disappear after it. Fix by making `dag_id=` a string literal or a local module-level constant defined earlier in the file, or create the subscription manually via the UI

## v2.2.0

- **Added:** `exchange=`/`routing_keys=`/`routing_key_ids=`/`routing_key_status=` parameters in `@rmq_trigger` — subscribe a DAG directly to a topic exchange instead of a pre-existing queue; the provider declares the exchange, its `.unrouted`/`.log` safety-net queues, a dedicated `rmq_watcher.sub.{dag_id}` queue, and keeps its bindings in sync with the routing keys declared in the decorator on every reconcile cycle

- **Added:** dependency `httpx` — async HTTP client for the Management API calls
- **Fixed:** `@rmq_trigger` stacked above a TaskFlow `@dag(...)` factory (the pattern used in every example DAG and in the README) crashed DAG import with `AttributeError: 'function' object has no attribute 'dag_id'` — `@dag(...)` returns an uncalled factory function, not a `DAG` instance, until invoked at the bottom of the file. The decorator now detects this case and defers subscription attachment to a wrapper that runs after the factory produces the real `DAG`; a clear `TypeError` is raised if decorator order is reversed or the input is neither a `DAG` nor a callable

## v2.1.0

- **Added:** `queues=[...]` parameter in `@rmq_trigger` — subscribe a single DAG to multiple RabbitMQ queues; a message from any of them triggers the DAG
- **Added:** `cooldown=N` parameter in `@rmq_trigger` — after the first matching message the DAG starts exactly once after N seconds; all messages in the cooldown window are ACKed silently; `cooldown=0` (default) keeps the existing immediate-trigger behaviour
- **Added:** DLX-based cooldown mechanism — no writes to Airflow DB; uses `rmq_watcher.pending.{dag_id}` (topic DLX queue, x-max-length=1) as a per-message TTL timer and `rmq_watcher.fire` (topic exchange + queue) as the trigger; RMQ infrastructure is created automatically by the plugin on startup
- **Added:** Fire consumer — subscribes to `rmq_watcher.fire`, extracts `dag_id` from `routing_key`, and calls `trigger_dag()` with an idempotent run_id (`rmq_cooldown__{dag_id}__{message_id}`) to prevent duplicates on redelivery
- **Added:** Hot-reload — changes to `cooldown` or `filter_data` in a DAG file are picked up on the next reconcile cycle without restarting the Scheduler
- **Added:** Orphaned pending-queue warnings — when a cooldown subscription is removed the plugin logs a WARNING with the queue name and the `rabbitmqadmin` delete command; subsequent reconcile cycles are silent
- **Added:** UI grouping — subscriptions sharing the same `group_key` (= dag_id when cooldown > 0) are shown as a single group row; `Cooldown` column added; Enable/Disable/Delete apply to all queues in the group
- **Added:** Multi-queue form — subscription form supports a dynamic list of queues (+ Add / ✕ remove); creates one DB row per queue within the same group
- **Changed:** `_ActiveSub` dataclass replaces parallel `_tasks` / `_sub_conn_ids` dicts in `RMQConsumerManager` — snapshot of the full sub dict drives change detection and hot-reload
- **Fixed:** fire consumer treated a missing `message_id` by generating a fallback UUID, which broke the idempotency guarantee on redelivery — now logs a warning and ACKs/skips the message instead
- **Fixed:** `reconcile()` silently skipped starting the fire task when its connection wasn't available right after provisioning — now logs a warning so the condition is visible
- **Limitation:** when cooldown is active `conf["body"]` and `conf["headers"]` in the triggered DAG run are empty — original message data is not preserved through the DLX chain

## v2.0.0

**RMQ Watcher Plugin** — reactive DAG triggering from RabbitMQ (fully backwards compatible with 1.x)

- **Added:** `RMQWatcherPlugin` — Airflow plugin that starts a background RabbitMQ consumer inside the Scheduler process. Incoming messages automatically trigger associated DAGs without polling, sensor tasks, or worker slots
- **Added:** `@rmq_trigger(queue, conn_id, filter_data)` decorator — attach RabbitMQ queue subscriptions directly to DAG definitions (Infrastructure as Code). Supports stacking multiple queues on one DAG
