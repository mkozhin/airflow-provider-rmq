# Очередь `{exchange}.log` копит весь трафик exchange'а без ограничения длины

**Решение, которое остаётся принять.** Чинить сейчас не стоит: на проде трафик
exchange-подписок мал, и последние 8 часов трафика занимают на брокере немного.
Пункт становится срочным, когда объём «поток exchange'а × 8 часов» начинает
заметно съедать свободный диск узла брокера. Проверка на брокере:

```
rabbitmqctl list_queues -p <vhost> name consumers messages message_bytes | grep '\.log'
```

**Как устроено.** `_ensure_exchange_infrastructure` (`consumer.py:3815`) на
каждом reconcile-цикле объявляет для exchange-подписки очередь `{exchange}.log`
(`consumer.py:3864`). Очередь durable, из аргументов у неё только
`x-message-ttl` (8 часов), и она привязана к exchange'у ключом `#`
(`consumer.py:3872`). Консьюмера у очереди нет, лимита длины тоже. В итоге в ней
всегда лежит полная копия последних 8 часов трафика exchange'а, включая
сообщения, адресованные другим системам.

**Последствия при большом трафике.** Например, 100 сообщений/с по 2 КБ дают
~2,9 млн сообщений и ~6 ГБ на каждый exchange, к которому подписан хотя бы один
DAG. На RabbitMQ 4.x classic-очередь держит сообщения в основном на диске, так
что опасность в диске, а не в памяти. При `disk_free_limit` брокер поднимает
disk alarm и блокирует публикацию во всём кластере, в том числе продюсерам вне
Airflow. При малом трафике цена другая: лишний диск и двойная запись каждого
сообщения, потому что оно пишется и в очередь получателя, и в `.log`. В Airflow
ничего из этого не видно, проявляется только на брокере.

**`.unrouted` при живой `.log` всегда пуста.** Alternate exchange
`{exchange}.unrouted` получает сообщение, только если оно не подошло ни одной
привязке. Ключ `#` у `.log` подходит любому routing key, поэтому
немаршрутизируемых сообщений не бывает: сообщение с ключом, на который не
подписан ни один DAG, попадает в `.log` и через 8 часов пропадает. README
(`readme.md:761`) говорит, что такие сообщения попадают в `.unrouted`, и это
неверно независимо от объёма трафика. Если убрать `.log`, `.unrouted` начнёт
получать весь трафик по ключам без подписчиков, и ей понадобится тот же лимит.

**Ограничение для любого решения в коде.** Аргументы существующей очереди не
меняются: если провайдер объявит `.log` с `x-max-length`, а на брокере она уже
создана со старыми аргументами, брокер ответит 406 `PRECONDITION_FAILED`.
`_provision_exchange_group` (`consumer.py:2307-2323`) считает это отказом всей
группы exchange'а: работающие подписки продолжают получать сообщения, но новые
DAG'и и изменения routing keys не применяются, и каждый цикл пишется ERROR.
Поэтому код обязан принимать уже существующую очередь как есть.

**Мера без кода.** Policy применяется к существующей очереди без пересоздания:

```
rabbitmqctl set_policy -p <vhost> rmq-exchange-log '^<exchange>\.log$' \
  '{"max-length":10000,"overflow":"drop-head"}' --apply-to queues
```

К очереди применяется одна policy, с наивысшим приоритетом: если на vhost уже
есть совпадающая, лимит добавляется в неё.

**Направления решения.**

1. *Скользящее окно, старое принимается как есть* (предпочтительное). Новые
   `.log` и `.unrouted` объявляются с `x-max-length` и `x-overflow=drop-head`;
   на 406 по уже существующей очереди открывается новый канал, очередь берётся
   пассивным declare, пишется WARNING с командой policy, провижининг
   продолжается. README описывает, что создаётся, сколько занимает, и что
   `.unrouted` пуста при живой `.log`. API не меняется.
2. *Убрать `.log`.* `.unrouted` оживает, и ей нужен тот же лимит и тот же
   обход 406. Старая `.log` с привязкой `#` копит дальше, пока её не удалят
   руками. Ломает тех, кто читает `.log`.
3. *`.log` по флагу декоратора.* Параметр нужно провести через AST-скан и
   `exchange_meta` и решить конфликт DAG'ов на одном exchange; остальное — как
   во втором варианте.
4. *Только README.* Предупреждение о размере и команда policy; умолчание
   остаётся без лимита.
