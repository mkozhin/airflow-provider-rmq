# Оператор и сенсор видят только голову очереди: за прогон разбирается один батч

**Симптом.** `RMQConsumeOperator.execute` делает ровно один
`hook.consume_messages(max_messages=...)` и разбирает, что пришло. Если своё
сообщение лежит за пределами батча, прогон возвращает пустой список зелёной
задачей. У `RMQSensor.poke` (`sensors/rmq.py:167`) то же самое, батчами по
`poke_batch_size`.

С `ack_unmatched=True` это не тупик: чужие сообщения уходят из
очереди насовсем, поэтому своё доходит до головы за несколько прогонов. Открытым
остаётся «за один прогон».

**Что закрыло бы.** Повтор `consume_messages` внутри одного `execute()`, пока не
набрано `max_messages` совпадений. К нему пристёгивается ещё три вещи: потолок
числа забранных за прогон сообщений, окно префетча на время цикла и правило,
какие отказы завершают цикл возвратом собранного.

**Почему не сделано вместе с `ack_unmatched`.** Цикл создаёт класс отказов,
которого сегодня нет вовсе: `consume_messages` вызывается один раз и до первого
`ack`, поэтому любое исключение оставляет очередь нетронутой и Airflow ретраит
задачу. С повтором между подтверждением совпадения и возвратом значения
появляется столько точек отказа, сколько кругов, и каждая теряет уже снятое с
брокера сообщение безвозвратно. За восемь раундов ревью плана
`20260903-filter-miss-ack-unmatched` треть всех находок пришлась на этот цикл,
и четыре из них были внесены правками по предыдущим находкам того же цикла.

**Что придётся решить, когда дойдут руки.**

- Условие спасения — не номер круга, а факт подтверждения: пока ни одно
  совпадение не подтверждено, сбой летит наружу; после первого `ack` завершает
  цикл возвратом собранного.
- Перехват — `except Exception`, а не перечень типов: `consume_messages`
  декодирует строгим `body.decode("utf-8")` (`hooks/rmq.py:676`), и бинарное
  тело даёт `UnicodeDecodeError` мимо любого перечня AMQP-ошибок. Смежное:
  [[sync-decode-raises-on-binary-body]].
- Перехват охватывает круг целиком: `hook.ack()` и `hook.nack()` тоже
  обращаются к каналу (`hooks/rmq.py:686-702`).
- Окно префетча обязательно. `qos` у оператора по умолчанию `None`, `basic_qos`
  не вызывается вовсе (`hooks/rmq.py:251-252`), брокер стримит очередь в клиент,
  а `channel.cancel()` (`hooks/rmq.py:681`) реджектит весь буфер с
  `requeue=True` — `BlockingChannel.cancel` в pika 1.4.4 гонит
  `basic_reject(..., requeue=True)` по `get_waiting_message_count()`. Без окна
  каждое сообщение за пределами батча получает доставку на каждом круге.
- `prefetch_count` в AMQP — short: размер круга ограничивается 65535.
- Цикл завершается на первом круге с `ERROR`, иначе сбойное сообщение
  возвращается в голову и передоставляется на каждом круге.
- Ничего из этого не касается ветки `ack_unmatched=False`: там цикла нет.

**Радиус.** Оператор и сенсор. Watcher и триггер к этому отношения не имеют — они
потребляют непрерывно.
