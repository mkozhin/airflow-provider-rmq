# Нелитеральный аргумент `@rmq_trigger` молча теряется

**Симптом.** `_parse_rmq_trigger_decorator`
(`airflow_provider_rmq/watcher/listener.py:450`) обходит kwargs вызова декоратора,
отбрасывает всё, чего нет в `_RMQ_TRIGGER_KWARGS` (`listener.py:420`), и остальное
пытается прочитать через `ast.literal_eval`:

```python
try:
    value = ast.literal_eval(kw.value)
except (ValueError, TypeError):
    continue                      # listener.py:491
kwargs[kw.arg] = value
```

`continue` выбрасывает kwarg из `kwargs` — без единой строки в логе. Достаточно
написать `queue=QUEUE_NAME` вместо `queue="orders"`, где `QUEUE_NAME` — модульная
или импортированная константа, чтобы аргумент исчез. Дальше последствия расходятся
надвое, в зависимости от того, какой именно kwarg потерян.

**Потерян маркер режима.** `queue=` / `queues=` / `exchange=` — единственный признак,
по которому выбирается режим подписки. Без него `build_subscriptions` не вызывается
вовсе, функция возвращает `[]` (`listener.py:494-495`), и подписка не появляется в
UI без какого-либо объяснения. Даже WARNING не пишется — в отличие от
нерезолвящегося `dag_id`, который пропускается с предупреждением.

**Потерян любой другой распознаваемый kwarg.** Маркер режима — литерал, подписка
**строится**, и вместо пропущенного значения `build_subscriptions`
(`airflow_provider_rmq/watcher/subscription_builder.py:28-40`) подставляет своё
сигнатурное умолчание. Три случая с прямыми последствиями:

- `conn_id=RMQ_CONN` → `conn_id="rmq_default"`. Подписка сохраняется в БД с чужим
  подключением, и consumer идёт **не на тот брокер**. Если `rmq_default` не
  существует, по подписке пишется `error` — про подключение, которого никто не
  называл;
- `filter_data=FILTER` → `filter_data=None`, то есть подписка **без фильтра**:
  сообщения, которые настоящая конфигурация отвергла бы, проходят и подтверждаются;
- `cooldown=COOLDOWN` → `cooldown=0`, то есть **immediate-режим** вместо cooldown:
  подписка не открывает pending-очередь и запускает DAG на каждом сообщении.

Тот же путь у `routing_key_status`. Exchange-режим защищён частично: если
нелитеральными оказались **оба** `routing_keys` и `routing_key_ids`,
`build_subscriptions` бросает `ValueError`, и подписка пропускается с WARNING. Если
нелитеральным оказался только один из них — набор routing-ключей молча урезается до
второго.

**Почему это важно.** Два последствия одного `continue` относятся к разным классам.
Первое видимо: подписки нет, и это заметно. Второе — нет: подписка есть, выглядит в
UI рабочей со статусом `listening`, и её поведение расходится с тем, что написано в
DAG-файле. Ни лога, ни строки в UI, ни ошибки — оператору не с чего начать.
Ограничение задокументировано как «Gotcha: literal arguments only» в
`docs/example_dags/rmq_watcher_jetstat_exchange.py`, но документация ловит только
того, кто её читал: `conn_id=CONST` и `filter_data=CONST` — ровно тот стиль, который
поощряет любой линтер, константа в шапке файла вместо литерала в декораторе.

**Направление решения (не проработано).** Минимум — WARNING на каждом пропущенном
kwarg с именем аргумента, `dag_id` и подсказкой про литералы; это снимает
невидимость, ничего не меняя по существу. Строже — отказываться строить подписку
целиком, если нелитеральным оказался хоть один распознаваемый kwarg: отсутствующая
подписка честнее подписки, которая слушает не тот брокер. Это тот же принцип, что
уже применён к нерезолвящемуся `dag_id`. Полное решение — тот же словарь модульных
констант, что резолвит `dag_id=` (см. [[ast-dag-id-resolution-incomplete]]),
переиспользованный и для аргументов `rmq_trigger(...)`; напрашивается делать оба
пункта одной задачей. Резолвинг констант уменьшит частоту, но не закроет случай:
вызовы функций и f-строки останутся нелитеральными.
