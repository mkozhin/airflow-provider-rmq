# Реестр `_status_writers` растёт всю жизнь процесса

**Симптом.** Писатель статуса заводится по `sub_id` при первом обращении
(`_status_writer`, `consumer.py:436`) и кладётся в процесс-глобальный
`_status_writers` (`consumer.py:432`, вставка на `:441`); удаления из реестра нет
нигде в продакшн-коде — `clear()` встречается только в тестовой фикстуре.
Мёртвые `sub_id` появляются штатно: `_sync_to_db` (через `_delete_absent_sub`,
`listener.py:1428`) удаляет `dag_file`-подписку, чей ключ не встретился в
четырёх доверенных сканах подряд, а `delete`, `edit_group` и Create на странице
Subscriptions удаляют и вставляют строки по воле оператора. Каждый удалённый id
навсегда удерживает в реестре своего писателя.

**Почему это не поведенческий дефект.** Цена одной записи — замок и пять полей
(`_StatusWriter.__init__`, `consumer.py:332-341`), порядок величины — десятки
записей на процесс. Финальный статус удалённой подписки при этом дописывает проход
по реестру в `_store_unwritten_statuses` (`consumer.py:1412`): именно для этого
реестр и обязан переживать подписку — строка живёт дольше, чем всё, что в неё пишет.

**Почему отложено.** Вывод писателя безопасен только когда им никто не
пользуется, а «никто» здесь включает брошенные таски — в том числе таски
менеджера, на смену которому после пересоздания event loop пришёл следующий:
реестр принадлежит процессу, и оба менеджера пишут через него. Связи
«брошенная таска → `sub_id`» в коде нет — `_abandoned` (`consumer.py:1266`)
держит объекты тасок, — поэтому механизм начинается с настоящего владения:
процесс-глобальная очередь на вывод, именование тасок, фиксированный порядок
двух замков. Новое разделяемое изменяемое состояние в модуле, где каждая из
трёх предыдущих попыток исправления уже порождала дефект того же класса, — цена
не в пользу механизма при десятках объектов из замка и пяти полей.
