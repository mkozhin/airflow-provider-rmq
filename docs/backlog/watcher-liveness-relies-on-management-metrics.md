# Проверка живости watcher'а опирается на устаревший сбор метрик Management API

**Контекст.** При заданном `management_url` проверка живости watcher'а
(`_probe_consumers`, `watcher/consumer.py:2953`) спрашивает брокер о своих
консьюмерах через `GET /api/consumers/{vhost}` (`get_queue_consumers`,
`utils/management.py:52`) и ищет в ответе точный тег каждой подписки. Этот
эндпоинт отдаёт данные, которые собирает подсистема метрик Management-плагина, а
она в RabbitMQ — устаревшая функция `management_metrics_collection`. На продовом
брокере (RabbitMQ 4.4.0, `GET /api/deprecated-features`) у неё статус
`permitted_by_default`: сбор метрик включён, проверка работает.

**Почему это важно.** Документация RabbitMQ
([Deprecated Features](https://www.rabbitmq.com/docs/deprecated-features),
[Management Plugin](https://www.rabbitmq.com/docs/management)) не говорит, что
отвечает `/api/consumers` при отключённом сборе метрик. Ожидаемое следствие —
успешный ответ с пустым списком. Для `_probe_consumers` это не сбой Management
API, а вердикт «консьюмеров нет»: теги подписок не подтверждены, после двух
таких проверок подряд подписки этого `conn_id` отменяются, а общее соединение
пересоздаётся. Живые консьюмеры перезапускались бы каждые несколько циклов, а
переход на пассивный declare, который срабатывает только на ошибках запроса, не
наступил бы никогда.

**Что переводит пункт в работу.** Перевод `management_metrics_collection` в
`denied_by_default` в очередной версии RabbitMQ или отключение сбора метрик на
продовом брокере.

**Направление решения.**

- Опора на AMQP-проверку: собственный канал клиента уже знает, держит ли он
  тег, а пассивный declare подтверждает, что соединение отвечает; Management
  API остаётся необязательным источником.
- Обнаружение отключённой статистики: признак в ответе Management API (или
  отдельный запрос), по которому пустой список консьюмеров считается «нет
  данных», а не отрицательным вердиктом, и проверка переходит на пассивный
  declare.
