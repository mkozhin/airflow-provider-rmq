# Умерший watcher-процесс не перезапускается, о его смерти никто не узнаёт сам

Watcher — дочерний процесс шедулера (`_spawn_child`, `listener.py:627`). Процесс, умерший
сам (OOM, segfault, SIGKILL), не перезапускается до рестарта шедулера: в процессе шедулера
нет ни потока, ни обработчика SIGCHLD, которые заметили бы его смерть (ADR 0008, раздел
«Перезапуска нет, работу показывают heartbeat и метрика»). До рестарта подписки не
обрабатываются, DAG'и по ним не запускаются.

Остановку видно: когда ни один watcher не подтверждает работу, главная страница Airflow
показывает красный баннер, а страница Subscriptions — мёртвую строку процесса и статусы
подписок как `unknown` (ADR 0012). Остаются три пробела:

- **Перезапуска нет.** Обработка подписок возвращается только с рестартом шедулера, который
  делает человек.
- **Push-уведомлений нет.** Баннер видит тот, кто открыл главную страницу Airflow; ни письма,
  ни сообщения в чат о смерти watcher'а не уходит.
- **Тревоги по отдельной реплике в HA нет.** Смерть watcher'а одной реплики при работающих
  других баннера не даёт и видна только строкой `dead` на странице Subscriptions. Связать
  строку heartbeat со своим `SchedulerJob` без кода в процессе шедулера нельзя.

Направления, не исключающие друг друга:

- **Мониторинг.** Довести StatsD Airflow до Prometheus и завести правило «нет прироста
  `cycle_completed` N минут» на каждый шедулер — это закрывает и уведомления, и тревогу по
  реплике. Кода провайдера не требует.
- **Самовосстановление в провайдере.** Проверять живость ребёнка из шедулера и
  перезапускать его — например, по `Popen.poll()` из хука листенера, который Airflow
  вызывает в процессе шедулера, или из отдельного потока-сторожа. Это пересмотр решения
  ADR 0008, и он должен учитывать петлю падений: ребёнок, умирающий сразу после старта,
  нельзя перезапускать без паузы.
