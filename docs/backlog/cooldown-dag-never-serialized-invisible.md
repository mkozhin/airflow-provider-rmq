# Cooldown-DAG, который не сериализуется никогда, виден только в логе

**Контекст.** Подписка с `cooldown > 0` DAG не запускает: сопоставленная
доставка заменяется плейсхолдером в `rmq_watcher.fire`, а по истечении окна
DAG триггерит fire-consumer. Его состояние — `_ConsumerState(None, …)`, то
есть строки на странице Subscriptions у него нет вовсе: `write` выходит на
`if self._sub_id is None: return`.

Когда триггер отвечает `DagNotFound`, обработчик fire-доставки возвращает
событие в очередь с растущей паузой, считает события по `dag_id` и пишет
строку в лог — INFO, а на каждом десятом событии одного DAG'а WARNING.
Статус консьюмера он держит на `listening`: его читает только проверка
живости соединения, и `listening` оставляет прогревающийся fire-consumer её
кандидатом. Порога, за которым прогрев становится ошибкой, у этой ветки нет:
один fire-consumer обслуживает все cooldown-DAG'и, и его единственное
состояние — не тот адрес, куда можно записать ошибку конкретного DAG'а.

**Почему это важно.** Пока прогрев временный, повторы его расшивают. Но
cooldown-DAG, который не станет сериализуемым никогда — удалён из папки,
сломан ошибкой импорта, отключён на другом инстансе, — даёт ровно ту же
картину: событие ходит по кругу с паузой в минуту, страница показывает все
подписки этого DAG'а здоровыми, и единственный след — строка в логе шедулера
на каждое событие, WARNING'ом на каждом десятом. Оператор, который смотрит на
страницу, отличить эти два случая не может.

**Второе следствие — общая голова очереди.** Очередь `rmq_watcher.fire`,
её консьюмер и `trigger_backoff` — одни на все cooldown-DAG'и. Пока событие
несериализуемого DAG'а возвращается в очередь, обработчик выдерживает паузу,
доросшую до 60 секунд, и на это время не берёт из очереди ничего: события
исправных cooldown-DAG'ов ждут своей очереди за ним. Один DAG, который не
станет сериализуемым, замедляет запуск по истёкшим окнам у всех остальных.

**Направление решения (не проработано).** Счётчик по `dag_id` на менеджере
уже есть — он выбирает уровень записи в логе. Решением было бы дать ему порог
и адресата: по превышении писать `error` в строки затронутых подписок по их
`sub_id`, а не в состояние fire-consumer'а. Отсюда следуют два
вопроса, которых нет на immediate-пути: откуда обработчику взять список
`sub_id` по `dag_id` (сегодня fire-доставка знает только routing key) и когда
такой счётчик обнулять — прицепления, привязанного к одной подписке, у
fire-consumer'а нет. Это отдельный дизайн.
