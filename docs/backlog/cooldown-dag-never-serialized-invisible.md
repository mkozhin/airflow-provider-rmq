# Cooldown-DAG, который не сериализуется никогда, виден только в логе

**Контекст.** Подписка с `cooldown > 0` DAG не запускает: сопоставленная
доставка заменяется плейсхолдером в `rmq_watcher.fire`, а по истечении окна
DAG триггерит fire-consumer. Его состояние — `_ConsumerState(None, …)`, то
есть строки на странице Subscriptions у него нет вовсе: `write` выходит на
`if self._sub_id is None: return`.

Когда триггер отвечает `DagNotFound`, обработчик fire-доставки возвращает
событие в очередь с растущей паузой и пишет строку в лог. Ни счётчика, ни
записи статуса в этой ветке нет, и это осознанно: один fire-consumer
обслуживает все cooldown-DAG'и, поэтому единственный счётчик на его состоянии
смешивал бы прогревы разных DAG'ов, а успех любого обнулял бы стрик
остальных.

**Почему это важно.** Пока прогрев временный, повторы его расшивают. Но
cooldown-DAG, который не станет сериализуемым никогда — удалён из папки,
сломан ошибкой импорта, отключён на другом инстансе, — даёт ровно ту же
картину: событие ходит по кругу с паузой в минуту, страница показывает все
подписки этого DAG'а здоровыми, и единственный след — повторяющаяся строка
INFO в логе шедулера. Оператор, который смотрит на страницу, отличить эти два
случая не может.

**Направление решения (не проработано).** Вести прогрев по каждому `dag_id`
отдельно: словарь стрик-счётчиков на состоянии fire-consumer'а с ключом
`dag_id`, и по превышении порога — запись `error` в строки затронутых
подписок по их `sub_id`, а не в состояние fire-consumer'а. Отсюда следуют два
вопроса, которых нет на immediate-пути: откуда обработчику взять список
`sub_id` по `dag_id` (сегодня fire-доставка знает только routing key) и когда
такой счётчик обнулять — прицепления, привязанного к одной подписке, у
fire-consumer'а нет. Это отдельный дизайн.
