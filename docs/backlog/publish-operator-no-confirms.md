# `RMQPublishOperator` считает публикацию успешной, не дождавшись брокера

**Контекст.** `RMQPublishOperator.execute`
(`airflow_provider_rmq/operators/rmq_publish.py`) публикует через
`RMQHook.basic_publish`, а тот — через `channel.basic_publish` pika без
`confirm_delivery()` и с `mandatory=False`. В AMQP это «выстрелил и забыл»:
вызов возвращается, как только фрейм ушёл в сокет. Брокер может ещё не принять
сообщение, отвергнуть его или не найти для него ни одной очереди — оператор об
этом не узнает и завершится зелёным.

**Где это теряет данные.**

- *Немаршрутизируемое сообщение.* Публикация в exchange, у которого нет
  биндинга под этот routing key (опечатка в ключе, очередь ещё не создана,
  биндинг снят). Без `mandatory` брокер молча отбрасывает сообщение. Задача
  зелёная, downstream ждёт сообщения, которого не было.
- *Брокер под resource alarm.* Публикующее соединение блокируется; pika
  `BlockingConnection` с `blocked_connection_timeout=300` (`hooks/rmq.py:146`)
  поднимет исключение только через пять минут, а до того `basic_publish`
  складывает фреймы в буфер и возвращается. Если задача завершится раньше и
  соединение закроется, буфер уходит вместе с ним.
- *Обрыв соединения после записи в сокет.* Сообщение, не дошедшее до брокера,
  никем не переотправляется: хук ретраит только установку соединения, не
  публикацию.

**Почему это важно.** Это единственный компонент провайдера, который *создаёт*
сообщения, и он единственный, у кого нет подтверждения от брокера. Для
пайплайнов, где задача публикует событие «данные готовы», зелёная задача без
доставленного сообщения — худший из исходов: об ошибке никто не узнает.

**Направление решения.** Задачи 3 и 4 плана
`docs/plans/20260703-reliability-hardening.md` ([[reliability-hardening-plan-stale]]):

- `RMQHook(..., publisher_confirms: bool = False)`; при включённом флаге
  `channel.confirm_delivery()` внутри `get_channel()`, чтобы переоткрытый
  канал получал его заново; `basic_publish(..., mandatory: bool = False)` с
  пробросом `UnroutableError`/`NackError`;
- `RMQPublishOperator(..., confirm: bool = True, mandatory: bool = False)`;
  nack или возврат превращаются в `AirflowException` с индексом сообщения в
  батче («message 3 of 7 was nacked»);
- `confirm=True` по умолчанию — поведенческое изменение, в CHANGELOG. Цена:
  один round-trip на сообщение; для батчей стоит подтверждать пачкой, pika
  `BlockingChannel` делает это сам при `confirm_delivery`.

Тесты: `confirm_delivery` вызывается по умолчанию и после переоткрытия канала;
nack на N-м сообщении даёт исключение с индексом; `mandatory=True` и возврат.
