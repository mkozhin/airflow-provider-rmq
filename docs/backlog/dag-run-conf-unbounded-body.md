# Тело сообщения кладётся в `dag_run.conf` без ограничения размера

**Контекст.** `_trigger_dag` (`airflow_provider_rmq/watcher/consumer.py:3739`)
собирает `conf` для run'а из декодированного тела сообщения и всех его
заголовков целиком. AMQP не ограничивает тело: сообщение в несколько мегабайт
штатно. `DagRun.conf` в Airflow 2.x — `PickleType`, хранится в строке
`dag_run`, копируется в контекст каждой task instance и отрисовывается на
странице run'а в UI.

**Что из этого следует.**

- Каждый run с большим телом — строка `dag_run` того же размера, навсегда (или
  до `airflow db clean`). Тысяча сообщений по 5 МБ — 5 ГБ в таблице, которую
  шедулер читает на каждом цикле.
- Страница run'а в UI пытается показать `conf` как JSON; на мегабайтах она
  тормозит или не открывается.
- `conf` попадает в шаблонный контекст задач и в логи там, где его печатают, а
  тело сообщения может содержать персональные данные — они оказываются в
  метабазе и в логах без ведома автора DAG'а.

Тот же путь у заголовков: `dict(message.headers or {})` без фильтра
(`consumer.py:3750`). README (`readme.md:646`, `800`) показывает `conf["body"]`
в примерах, но о размере тела ничего не говорит.

**Чего не хватает для решения.** Неизвестны реальные размеры тел на живых
установках. Если сообщения — короткие события в JSON, вопрос закрыт
документацией «тело попадает в conf целиком». Если встречаются большие, нужна
граница: tunable `rmq_watcher_max_body_bytes` с умолчанием порядка 64 КБ,
тело сверх неё обрезается, в `conf` добавляется `body_truncated: true` и
`body_size`, а полный вариант DAG забирает сам по `message_id`. Альтернатива
— параметр декоратора `include_body=False` для подписок, которым нужно только
событие, а не его содержимое.
