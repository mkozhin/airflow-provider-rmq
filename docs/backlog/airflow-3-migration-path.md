# Дизайн watcher'а не переносится на Airflow 3, а у Airflow 3 есть свой ответ на ту же задачу

**Контекст.** Пин `apache-airflow>=2.9.0,<3.0.0` честный: провайдер живёт на
ветке 2.x. Но стоит записать, *что именно* держит его там, потому что это не
одна деталь, а сама конструкция watcher'а:

- дочерний процесс шедулера с asyncio-петлёй
  (`python -c <bootstrap> airflow_provider_rmq.watcher.runner`), который listener запускает
  в `on_starting` и останавливает в `before_stopping`, и определение «мы в
  шедулере» по стеку вызовов (`RMQWatcherListener.on_starting` в `listener.py`);
- прямой ORM к метабазе из плагина: `DagModel`, `serialized_dag` через
  `trigger_dag`, собственные таблицы через `airflow.settings.engine`;
- вызов внутреннего `airflow.api.common.trigger_dag` из потока;
- страница на Flask-AppBuilder (`appbuilder_views`, `flask_blueprints`) и
  выдача прав роли `Op` через FAB security manager;
- `DagModel.is_active` в бейдже и в проверке перед триггером.

В Airflow 3 (проверять по факту при переходе, здесь — по документации на дату
записи): FAB-страницы плагинов и `appbuilder_views` уходят, плагины UI пишутся
под FastAPI/React; `is_active` переименован и инвертирован; внутренний API
триггера сменил место; прямой доступ к метабазе из задач запрещён (для
операторов и сенсора провайдера это не проблема — они в базу не ходят).

**Что предлагает сам Airflow 3.** Событийное расписание встроено:
`AssetWatcher` поверх `MessageQueueTrigger` из провайдера
`common-messaging`. Триггер живёт в **triggerer'е**, слушает очередь и при
сообщении публикует событие asset'а, на которое DAG запланирован. Это закрывает
разом два пункта этого бэклога и один открытый план:

- HA: triggerer'ы распределяют триггеры между репликами сами — лидер-лок из
  reliability-hardening и кэш статусов между репликами
  ([[status-cache-stale-across-replicas]]) становятся ненужными;
- пул соединений watcher'а с метабазой
  ([[trigger-dag-burst-exhausts-watcher-db-pool]]) — запуск идёт через события
  asset'а, а не через `trigger_dag` из 32 потоков.

Ограниченные по времени шаги, которые нужны AMQP-реализации `MessageQueueTrigger`, уже
есть в `RMQTrigger`: подключение, канал, declare, `get`, `consume` и ACK — каждый под
`connect_timeout` / `rpc_timeout`, с повтором попытки — и переносятся туда как есть.

Чего у встроенного механизма нет и что пришлось бы нести самим: cooldown через
DLX, exchange-режим с provisioning биндингов, страница Subscriptions,
фильтрация по телу, детерминированный `run_id` по `message_id` — и, что
важнее, вся диагностика живости, которой в triggerer'е нет и которая там
нужна не меньше.

**Чего не хватает для решения.** Даты перехода прода на Airflow 3. Пока её нет,
ценность любой работы здесь нулевая, а цена — двойная поддержка. Как только
она появится, первый шаг — прототип `RMQMessageQueueTrigger` под протокол
`common-messaging` на 3.x, чтобы измерить, сколько из нынешнего watcher'а
действительно нужно переносить, а сколько закрывает платформа. Второй шаг —
решить судьбу UI: без FAB это отдельный фронтенд.
