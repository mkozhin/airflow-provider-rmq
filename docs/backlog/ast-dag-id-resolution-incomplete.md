# AST-резолвинг `dag_id` не покрывает сложные и динамические случаи

**Контекст.** Watcher читает DAG-файлы через `ast`, не исполняя их (DAG-код в процессе
watcher'а не исполняется: зависший импорт занял бы воркер пула цикла и держал бы import
lock'и модулей). Чтение файла живёт в `airflow_provider_rmq/watcher/dag_file_scan.py`:
`_read_file_triggers` (`dag_file_scan.py:956`) собирает подписки файла, а `dag_id` для
каждой функции с `@rmq_trigger` вычисляет `_static_dag_id` (`dag_file_scan.py:732`). Тот
же код при импорте DAG-файла прогоняет декоратор (`_verify_static_readability`,
`dag_file_scan.py:1136`).

Резолвится строковый литерал (`dag_id='my_dag'`) и строковая константа файла
(`DAG_NAME = 'my_dag'` → `dag_id=DAG_NAME`, присвоенная ровно один раз на верхнем
уровне выше функции модульного уровня), включая позиционную форму `@dag(DAG_NAME)` и
`@dag('my_dag')`. Механизм описан в
`docs/plans/completed/20260807-ast-dag-id-constant-resolution.md`.

Что **не** резолвится:
- f-строки и конкатенация, даже если все части — литералы/константы:
  `dag_id=f"{PREFIX}_{SUFFIX}"`, `dag_id=PREFIX + '_suffix'`;
- вызовы функций: `dag_id=make_dag_id(name)`;
- **импортированные константы**: `from common.constants import DAG_NAME`
  → `dag_id=DAG_NAME`. Вероятно, самый частый реальный вариант после
  локальной модульной константы: значение живёт в другом файле, а
  статический анализ читает только текущий;
- **распаковка аргументов декоратора**: `@dag(**{"dag_id": "real"})` или
  `@dag(**DAG_KWARGS)`. Для аргументов `@rmq_trigger` распаковка словаря-константы
  файла (`**RMQ_OPTS`) читается, а для `@dag(...)` — нет: наличие распаковки
  детектируется, но извлечь `dag_id` даже из литерального словаря парсер не пытается;
- значения, вычисляемые внутри цикла или на основе конфига, когда один
  файл генерирует несколько DAG с разными `dag_id` (dag-factory паттерн:
  `for cfg in CONFIGS: create_dag(cfg)`, где `dag_id` зависит от `cfg`), и любые
  константы в DAG'е, объявленном внутри функции-фабрики. Это принципиально не решается
  статическим AST-анализом одного присваивания — нужен либо более широкий
  constant-folding (f-строки/конкатенация из уже известных констант), либо отдельный,
  explicit-путь регистрации subscription для таких DAG (например через существующий
  `source='ui'`), либо что-то ещё.

**Почему это важно.** Нерезолвимый `dag_id` на функции с `@rmq_trigger` даёт видимую
ошибку, а не тихую: watcher не регистрирует ни одной подписки файла и пишет ERROR
(`cannot statically resolve dag_id`), а декоратор при импорте бросает
`RMQTriggerNotStaticError`, и Airflow показывает файл как Broken DAG вместе со всеми его
DAG'ами. Цена — такие DAG'и вообще не могут носить `@rmq_trigger`: факторируемые
DAG-конфиги и DAG'и с импортированными константами приходится переписывать на литералы
или константы файла, а подписку для них — заводить вручную через UI на DAG без
декоратора. Для `exchange=`-подписок UI-пути нет вовсе, там `dag_id` обязан быть
статически резолвимым.

**На кого влияет.** На данный момент ни одного реального DAG с f-строкой
или dag-factory-генерацией `dag_id` в связке с `@rmq_trigger` не найдено —
это профилактическая задача, не действующий баг. Ценность решится, когда такой DAG
понадобится на проде.
