# Ни один тест не разговаривает с настоящим RabbitMQ

**Контекст.** Набор из ~1 100 тестов целиком юнитовый: `aio_pika`, `pika`,
`httpx` и метабаза подменяются моками. CI (`.github/workflows/publish.yml`)
гоняет его на трёх версиях Python и на этом останавливается. Документ
`docs/live-verification.md` держит 17 сценариев ручной проверки на живом стенде,
и ни один из них не прогонялся ни разу.

**Почему это важно.** Два инцидента, определившие последние два месяца работы,
нашлись на проде, а не в тестах, и оба не могли найтись на моках:

- зомби-соединение после перезагрузки брокера (ADR-0007): объект `aio_pika`, у
  которого `is_closed` False и нет транспорта, — поведение библиотеки, которое
  мок воспроизводит только если автор мока уже знает о нём;
- спин сообщения на промахе фильтра ([[filter-miss-spins-until-ttl]]): 288 000
  передоставок за TTL — арифметика брокера, а не кода провайдера.

Тесты на моках проверяют, что код делает то, что автор *думает* о брокере.
Каждый следующий слой защиты (rate limit на пересоздание, nonce в теге,
двухуровневая проверка живости) добавлял допущения о поведении `aio_pika` и
RabbitMQ, и ни одно из них не проверено против них самих. Это главный
непокрытый риск проекта: чем больше в watcher'е логики восстановления, тем
больше в нём предположений, которые можно проверить только на брокере.

**Направление решения.** Отдельная job в CI с service-контейнером
`rabbitmq:4-management` и sqlite-метабазой Airflow (`airflow db migrate`),
маркер `pytest -m integration`, запуск по тегу и по ручному триггеру, чтобы
не замедлять обычные прогоны. Первые сценарии, каждый — на реальном брокере
и реальном `trigger_dag` в sqlite:

1. подписка прицепляется, сообщение запускает DAG, `dag_run` появляется с
   ожидаемым `run_id` и `conf`;
2. промах фильтра: сообщение возвращается в очередь и не подтверждается,
   совпавшее — подтверждается (и замер числа передоставок за 5 секунд как
   регрессионный порог для [[filter-miss-spins-until-ttl]]);
3. cooldown: маркер в pending-очереди, TTL истекает, fire-consumer запускает
   DAG ровно один раз при трёх сообщениях в окне;
4. `rabbitmqctl close_connection` под consumer'ом: проверка живости замечает,
   соединение пересоздаётся, consumer возвращается за два цикла;
5. удаление очереди под consumer'ом: `basic.cancel` от брокера, тег исчезает
   из канала, строка становится `error`, а после повторного создания очереди
   — `listening`;
6. quorum-очередь с `delivery-limit=3`: поведение при трёх nack подряд;
7. Management API: `GET /api/consumers` видит наш тег с точным именем; без
   тега `management` — 401 и переход на passive declare;
8. resource alarm (`rabbitmqctl set_vm_memory_high_watermark 0.0001`):
   consumer продолжает подтверждать, publish cooldown-маркера уходит в backoff
   и не теряет доставку.

Стоимость: около дня на обвязку и по часу на сценарий. Это дешевле любого
следующего слоя защиты в `consumer.py` и, в отличие от него, проверяет
предыдущие.

Смежное по CI: [[ci-no-min-airflow-version]].
