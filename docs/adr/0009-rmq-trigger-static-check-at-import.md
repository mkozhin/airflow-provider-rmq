# `@rmq_trigger` сверяет свой вызов со статическим чтением watcher'а при импорте DAG-файла

Watcher находит подписки, читая DAG-файлы через `ast` и не исполняя их. Декоратор же
получает аргументы, вычисленные Python'ом при импорте. Всё, что скан не читает, —
импортированная константа, вызов функции, f-строка, одноимённая обёртка `rmq_trigger` из
другого модуля, — даёт расхождение: DAG в Airflow работает с одними аргументами, а watcher
регистрирует подписку с другими (умолчание вместо `conn_id`, подписку без фильтра) или не
регистрирует её вовсе. Такая ошибка не видна ни в UI, ни в логе DAG'а: сообщения приходят не
туда или не приходят.

Решение — один парсер и проверка в обоих процессах:

- статическое чтение файла живёт в `watcher/dag_file_scan.py` и импортирует только
  стандартную библиотеку и `subscription_builder`. Его вызывают и watcher (скан папки DAG'ов),
  и декоратор (внутри DAG processor'а);
- декоратор при построении DAG'а прогоняет это чтение по файлу своего вызова
  (`_verify_static_readability`) и бросает `RMQTriggerNotStaticError` — это `ValueError`, —
  если watcher не сканирует файл, отказал бы файлу, не нашёл бы вызов, вычислил бы другой
  `dag_id` или прочитал бы другие значения. Импорт падает для всего файла: Airflow
  показывает плашку Broken DAG с перечнем проблем, и пропадают все DAG'и файла, включая те,
  на которых `@rmq_trigger` нет;
- скан читает `rmq_trigger` и `@dag(...)` только связанными импортом с декоратором
  провайдера и с декоратором Airflow (`airflow.decorators.dag`, `airflow.models.dag.dag`):
  одноимённая обёртка другого модуля может передать декоратору другие аргументы или дать
  DAG'у другой `dag_id`, чем видно в файле, и такой файл отвергается в обоих процессах.
  Имя разрешается в области видимости, где выполняется декоратор: учитываются привязки
  модуля выше функции, `global` в любой функции и привязки объемлющей фабрики, а локальные
  имена других функций, лямбд и включений — нет. Для DAG-функции, объявленной
  непосредственно в фабрике — обычной `def` без декораторов, не `async` и без `yield`, —
  привязка модуля ниже `def` фабрики не учитывается, если файл упоминает фабрику только в вызовах и
  каждый вызов выполняется на уровне модуля один раз до неё (`dag = create_dag()`); вызов
  фабрики после привязки, из функции, класса, лямбды, включения или цикла отвергает файл,
  как и упоминание без вызова (`FACTORIES.append(create_dag)`) и фабрика, которую файл не
  упоминает вовсе: её вызовет кто-то другой, когда модуль уже выполнился. Двухуровневая
  фабрика, класс между фабрикой и DAG-функцией, `async def`, генератор и фабрика с
  декоратором (`@register`) могут выполнить `def` DAG-функции позже вызова, поэтому ниже
  них учитывается любая привязка модуля;
- ниже первого `@rmq_trigger(...)` функции скан допускает только `@rmq_trigger(...)` и
  `@dag(...)`: другой декоратор там может изменить DAG незаметно для скана (без
  `functools.wraps` он переименовывает функцию, по имени которой назван DAG без `dag_id`), и
  файл отвергается в обоих процессах. Декораторы выше первого `@rmq_trigger(...)`
  оборачивают его результат и не читаются;
- watcher отказывает всему файлу, если хоть один его `@rmq_trigger` не читается статически:
  ни одна подписка файла не регистрируется, пишется один ERROR со всеми проблемами, прежние
  строки уходят через счётчик промахов. Отказ на уровне файла, а не вызова, потому что импорт
  того же файла в DAG processor'е падает целиком: подписка соседнего DAG'а, оставленная
  watcher'ом, потребляла бы сообщения для DAG'а, которого в Airflow уже нет
  (`consumer.py` подтверждает и теряет такие доставки);
- проверка читает и разбирает файл один раз на версию на диске (inode, время изменения,
  размер), сколько бы вызовов `@rmq_trigger` в нём ни было, — иначе файл с сотнями DAG'ов
  разбирался бы квадратично и упирался бы в `dagbag_import_timeout`.

## Considered Options

- Умолчания и WARNING. Отклонено: подписка работает вопреки тому,
  что объявлено в файле, а единственный сигнал — строка в логе шедулера, которую никто не
  связывает с конкретным DAG'ом.
- Отказ отдельному вызову, а не файлу. Отклонено: импорт файла в DAG processor'е падает
  целиком, и подписки соседних DAG'ов, которые watcher оставил бы, работали бы на DAG'и,
  которых в Airflow нет.
- Исполнять DAG-файлы в watcher'е. Отклонено: watcher живёт рядом со шедулером, исполнение
  чужого кода на каждом цикле — это побочные эффекты импорта, время и память шедулера.
- Выбрано: один парсер, ошибка импорта всего файла в DAG processor'е, отказ всему файлу в
  watcher'е.

## Ограничения

- `rmq_trigger`, переэкспортированный другим модулем под другим именем
  (`from common import trig`), для скана не `rmq_trigger`: `@trig(...)` обрывает импорт, а
  прочие подписки файла watcher продолжает регистрировать.
- Одноимённая обёртка `dag` из другого модуля (`from company import dag`) на функции с
  `@rmq_trigger` отвергается, даже если передаёт `dag_id` без изменений: скан её не исполняет
  и не может доказать, какой `dag_id` она даст. Такой файл импортирует `dag` из
  `airflow.decorators`.
- Декоратор ниже `@rmq_trigger` отвергается, даже если он не меняет DAG (обёртка с
  `functools.wraps`, логирующий декоратор): скан его не исполняет. Такой декоратор ставится
  выше первого `@rmq_trigger(...)`.
- Фабрика с `@rmq_trigger` вне `DAGS_FOLDER` или в файле, который отсекает `.airflowignore`,
  обрывает импорт («does not scan»): watcher такого файла не видит. Скрытые каталоги и файлы
  с точкой в имени watcher сканирует, как их загружает Airflow
  ([ADR 0010](0010-watcher-lists-dag-folder-like-airflow.md)).
- Проверка выполняется, только когда при импорте исполняется хотя бы один `@rmq_trigger`
  файла. В файле, где каждый вызов стоит в фабрике, которую файл не вызывает, или под ложным
  `if`, единственный сигнал — ERROR watcher'а.
- Проверка читает файл с диска в момент построения DAG'а, отдельно от исходника, который
  скомпилировал импорт. Файл, подменённый между ними (обновление git-sync посреди импорта),
  может уронить один разбор; следующий разбор проверяет ту же версию, что импортирует.
- `DagBag(dag_folder=...)` в CI и тестах требует `DAGS_FOLDER`, указывающего на ту же папку,
  иначе каждый DAG с `@rmq_trigger` падает с «does not scan».
