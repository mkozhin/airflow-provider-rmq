# Промах фильтра: подтверждение по просьбе подписки

## Overview

Сообщение, не подходящее ни одной подписке, из конструкции ADR-0002 не выходит:
брокер возвращает его в голову очереди, потребитель получает его снова, снова не
пропускает и снова возвращает. Круг занимает фиксированную паузу 0,1 с внутри
`nack_and_sleep`, то есть цикл идёт с частотой около 10 оборотов в секунду и
заканчивается только с истечением TTL сообщения. Замерено на рабочей установке
2026-08-28, очередь `services.mail.donstroy.success` (classic, TTL 8 часов, одна
подписка): +197 передоставок за ~20 секунд, порядка **288 000 передоставок одного
сообщения** за восемь часов.

Та же стратегия стоит во всех четырёх циклах потребления, и в трёх из них она
даёт не нагрузку, а **неверный результат**: `RMQConsumeOperator` с
`max_messages=100` при ста чужих сообщениях в голове возвращает пустой список
зелёной задачей, `RMQSensor.poke` — то же батчами, `RMQTrigger` в pull-режиме
крутит десять оборотов в секунду в процессе triggerer'а всё время ожидания
сенсора.

Работа даёт три вещи:

1. **`ack_unmatched`** — подписка может попросить подтверждать не прошедшие
   фильтр сообщения. Круг тогда не возникает вовсе: каждое сообщение доставляется
   один раз. Это ответ для случая, когда очередь принадлежит подписке.
2. **Различение промаха и сбоя фильтра.** Сейчас исключение из
   `filter_callable` неотличимо от «не совпало», и с подтверждением это стоило бы
   безвозвратной потери целого батча на минуту недоступности внешнего сервиса.
3. **Видимость.** Сейчас промах фильтра не виден нигде: ни строки в логе, ни
   метрики.

**При умолчаниях не меняется ничего.** Пауза остаётся фиксированной, requeue
остаётся поведением по умолчанию, добавляются только строки в логе и метрика.

**Асинхронный путь — общий чокпоинт есть.** `nack_and_sleep`
(`airflow_provider_rmq/utils/amqp.py:276`) сейчас без состояния: принимает только
сообщение, делает `nack(requeue=True)` и спит 0,1 с. Её вызывают `match_and_ack`
(`utils/amqp.py:304`) и watcher напрямую (`watcher/consumer.py:3246`);
`match_and_ack` вызывает триггер из `_handle_message` (`triggers/rmq.py:90`).
Продакшн-вызовов ровно два, вызов `match_and_ack` один, тестовых вызовов восемь.

**Watcher через `match_and_ack` не ходит.** Он делает `match()` и на совпадении
уходит в `_handle_cooldown_delivery` / `_handle_immediate_delivery`
(`watcher/consumer.py:3245-3255`); общий чокпоинт есть только у ветки промаха.
Сброс счётчика на совпадении обязан звать тот, кто получил совпадение.

**Consumer читает не строку, а проекцию.** `_read_active_subs`
(`listener.py:635-643`) собирает dict из шести жёстко перечисленных ключей —
`id`, `dag_id`, `queue_name`, `conn_id`, `filter_data`, `cooldown` — и он уходит
через `reconcile(active_subs)` в `_sync_consumer_tasks` и далее в
`_consume_subscription(sub)`. Ключ, не добавленный в эту проекцию, до consumer'а
не доедет никогда, какой бы ни была колонка в базе.

**Перезапуск таски решает whitelist.** `_subs_changed`
(`consumer.py:1686-1698`) сравнивает ровно пять полей — `queue_name`, `dag_id`,
`cooldown`, `filter_data`, `conn_id`, — и только его срабатывание перезапускает
consumer-таску (`consumer.py:1565-1575`). Запущенная таска читает `sub` один раз
на старте и живёт до отмены, поэтому поле, отсутствующее в этом списке, правкой
в UI не подействует до реконнекта или рестарта.

**Обработчиков формы три, а не два.** `subscription_form.py:3-5` перечисляет
`create()`, `edit()` и `edit_group()`; в коде — `views.py:348/376`, `:416`,
`:576/621`. `edit_group` строки не обновляет, а сносит и пересоздаёт
(`views.py:613-617`), после чего `upsert_subscription` присваивает поля
безусловно (`models.py:209-213`). Шаблон формы один: `subscription_form.html`.

**Фильтр не различает промах и сбой.** `MessageFilter.matches`
(`utils/filters.py:40-57`) ловит любое исключение `filter_callable`, пишет
WARNING и возвращает `False`. Вызовов три: `utils/amqp.py:272` внутри `match()`,
`operators/rmq_consume.py:83`, `sensors/rmq.py:147`.

**Остаток батча у сенсора фильтром не оценён.** `RMQSensor.poke`
(`sensors/rmq.py:141-156`) выходит на первом совпадении и возвращает
`messages[i + 1:]` через `nack(requeue=True)` — эти сообщения фильтр не видел, и
подтверждать их нельзя ни при каких настройках.

**Prefetch у оператора задаётся пользователем.** `basic_qos` вызывается только
когда передан `qos` (`hooks/rmq.py:175-180`), readme документирует пример
`qos={"prefetch_count": 10}`. Стратегия, удерживающая чужие сообщения unacked,
упирается в это окно: заполнив его, потребитель перестаёт получать доставки,
`consume_messages` выходит по `inactivity_timeout` с пустым результатом, и цикл
читает это как «очередь пуста». Подтверждённые сообщения окна не держат, поэтому
добор безопасен только на ветке подтверждения.

**`_ConsumerState` переживает переприцепления.** Создаётся в
`_launch_subscription_task` (`watcher/consumer.py:1521`) один раз на
consumer-таску, а `_consume_subscription` (`consumer.py:3182`) крутит внутри себя
цикл переподключений. Рядом стоит комментарий (`consumer.py:3202-3204`), по
которому `trigger_backoff` и `publish_backoff` создаются один раз на всю задачу.

**Миграция колонок обобщена, Alembic в проекте нет.** `ensure_table_exists`
(`models.py:134-149`) делает `create_all(checkfirst=True)`, затем
`_add_missing_columns` (`models.py:93-131`) инспектирует каждую таблицу и выдаёт
`ALTER TABLE {table} ADD COLUMN {name} {type}` на каждую колонку модели, которой
в таблице нет. DDL собирается только из имени и типа: `NOT NULL` в него не
попадает, и код прямо это документирует — «columns are added as nullable
regardless of the model». Отсюда требование объявлять колонку `nullable=True`:
иначе новая установка получит её NOT NULL через `create_all`, а обновлённая
nullable через `ALTER TABLE`, и схемы разъедутся.

**Путь параметра подписки.** `rmq_trigger` (`watcher/decorators.py:12-23`) →
`build_subscriptions` (`watcher/subscription_builder.py:28-40`) →

(`models.py:177-188`) → строка → проекция `_read_active_subs` → consumer.

**Уникальность строки — `(dag_id, queue_name, conn_id)`** (`models.py:29-31`), то
есть два разных DAG'а на одну очередь разрешены и ничем не отмечаются. Бейдж

**Брокер для интеграционных тестов проверен.** RabbitMQ 4.2.0 / Erlang 27.3.4.5,
vhost `test`, пользователь с тегом `management`. Работают classic- и
quorum-очереди, topic-обменник, DLX. `messages` в `/api/queues` отстаёт на

**ADR-0002** (`docs/adr/0002-four-consume-loops-not-unified.md`) обосновывает
requeue тем, что «чужое для одной подписки сообщение нужно другой», и называет

одна подписка», и ADR правится по существу.

## Solution Overview

**`ack_unmatched` — булев параметр подписки, умолчание `False`.** При `False`
поведение сегодняшнее: не прошедшее фильтр сообщение возвращается в очередь. При
`True` оно подтверждается и уходит. Круг тогда не возникает вовсе — не «реже», а
не возникает: каждое сообщение доставляется один раз.

Значение принадлежит подписке, а не подключению: `rmq_default` общий для всего
инстанса, и настройка на нём включила бы отбрасывание везде. Поэтому
`@rmq_trigger(..., ack_unmatched=True)`, колонка в строке подписки, чекбокс в
форме; у `RMQConsumeOperator`, `RMQSensor` и `RMQTrigger` — одноимённый параметр
задачи. Connection extra в этом не участвует.

**Параметр обязан пройти весь путь до consumer'а.** Колонки в базе мало: consumer
читает проекцию `_read_active_subs` из шести ключей, а перезапуск таски решает
whitelist `_subs_changed` из пяти полей. Оба списка расширяются, иначе значение
либо не доедет, либо доедет один раз и не поменяется по правке в UI.

**`ack_unmatched=True` не задействует DLX.** Dead-lettering срабатывает на reject,
истечение TTL и переполнение, но не на подтверждение. Сообщение просто исчезает.
Это записывается в обоих readme прямым текстом.

**Подтверждается только то, что фильтр оценил и отверг.** Два следствия. Первое:
остаток батча сенсора после раннего выхода фильтром не оценивался, поэтому
возвращается в очередь всегда, независимо от параметра. Второе: сбой вычисления
фильтра — не промах. `MessageFilter` начинает различать «совпало», «не совпало» и
«не смогли вычислить»; последнее ведёт себя как сегодня — WARNING и возврат в
очередь — и в ветку подтверждения не попадает никогда.

**Пауза остаётся фиксированной.** Растущая пауза отличала бы залипшее сообщение
от бэклога только по памяти о конкретных сообщениях, которой здесь нет: флаг
`redelivered` значит «сообщение кому-то доставлялось», а не «это тот же
экземпляр». На возвращённой пачке из тысячи чужих сообщений каждое приходит
`redelivered`, и растущая пауза сделала бы такой бэклог многократно дороже
сегодняшнего. Лекарство от круга — `ack_unmatched`, а не пауза.

**Видимость безусловна и одинакова во всех четырёх местах.** Счётчик промахов
подряд, WARNING на каждой степени десяти (100, 1 000, 10 000 …) с именем очереди
и подсказкой проверить `filter_data`, метрика `rmq_watcher.filter_missed` в
watcher'е. При `ack_unmatched=True` тот же счётчик считает отброшенные: это
единственная защита от неверно настроенного фильтра, тихо съедающего очередь.
Метрика ставится только в watcher'е — у оператора, сенсора и триггера метрической
обвязки нет, и префикс `rmq_watcher` в них был бы неправдой.

**Оператор с подтверждением добирает.** Одного вызова `consume_messages` мало:
очередь со 150 чужими сообщениями и одним своим при `max_messages=100` отдала бы
пустой список даже с подтверждением. Поэтому на ветке подтверждения оператор
повторяет забор, пока не наберёт `max_messages` совпадений, не исчерпает потолок
слива или не получит пустой батч. Это безопасно именно здесь: подтверждённые
сообщения окно prefetch не держат.

**Одна очередь — одна подписка: рекомендация, не запрет.** Уникальный ключ строки
не меняется, две подписки на одну очередь остаются возможны. В readme это
записывается как задуманная конфигурация, а на странице Subscriptions включённые
строки с одинаковыми `queue_name` и `conn_id` получают бейдж — тем же механизмом,
что `⚠ dag not found`.

**Чего эта работа не делает.** Оператор и сенсор на очереди, где чужие сообщения
нужны кому-то ещё, по-прежнему видят только голову очереди: посмотреть мимо неё
можно лишь удержанием чужих unacked, а оно упирается в `qos.prefetch_count`
самого оператора и вредит другим потребителям. Ответ для этого случая —
`ack_unmatched=True` на очереди, которая принадлежит подписке.

## Technical Details

**`FilterVerdict`** — новый enum в `utils/filters.py`: `MATCH`, `MISS`, `ERROR`.
`MessageFilter.evaluate(properties, body) -> FilterVerdict` заменяет `matches` в
трёх местах вызова; `matches` остаётся как `evaluate(...) is MATCH` для любого
кода вне провайдера. `ERROR` возвращается там, где сегодня перехватывается
исключение `filter_callable`, и WARNING остаётся на том же месте.

**`FilterMissState`** — новый класс в `utils/amqp.py`:

| поле | смысл |
|---|---|
| `queue_name` | для текста WARNING'а |
| `ack_unmatched` | решение, уже прочитанное из подписки или параметра задачи |
| `streak` | промахов подряд; на степенях десяти пишется WARNING |

Ни ключей сообщений, ни словарей, ни backoff, ни обращений к брокеру, ни
корутин — объект одинаково работает на асинхронном и синхронном пути. Владельцы:
у watcher'а — поле в `_ConsumerState`, создаваемое один раз на consumer-таску; у
триггера — кадр `run()`, откуда состояние идёт в `_run_push` и `_handle_message`;
у оператора и сенсора — прогон задачи.

Методы: `on_match()` сбрасывает `streak`; `on_miss()` наращивает его и пишет
WARNING на степени десяти.

**Поток промаха** на асинхронном пути:

```
evaluate(message, filter)
  MATCH → state.on_match(), затем ack и обработка
  ERROR → WARNING, nack(requeue=True), sleep 0.1 с — как сегодня
  MISS  → state.on_miss()
          ack_unmatched is True  → message.ack()
          ack_unmatched is False → message.nack(requeue=True), sleep 0.1 с
```

**Колонка** `ack_unmatched = Column(Boolean, nullable=True)` в `RMQSubscription`.
`nullable=True` обязательно: `_add_missing_columns` добавляет колонку без
`NOT NULL` независимо от модели, так что `nullable=False` дал бы разную схему на
новой и на обновлённой базе. `None` читается как `False`. Своего шага миграции
колонке не нужно — обобщённый путь `models.py:93-131` добавляет её сам.

## Post-Completion

*Требует доступа или решения оператора инсталляции*

**Немедленная мера, не ждущая релиза.** Пока правка не выкачена, частоту кругов на
залипшем сообщении можно сбить со стороны брокера: quorum-очередь с
`x-delivery-limit` убирает сообщение сама. Ограничение — механизм существует
только для quorum-очередей, и тип очереди на лету не меняется.

**Радикальное решение вне провайдера.** Продублировать признак, по которому
фильтрует DAG, в routing key при публикации. Тогда topic-биндинг отсекает чужие
сообщения на брокере, и в очередь подписки они не попадают вовсе. Требует правки
на стороне продюсера.

**Проверка на живой установке.** Замерить частоту передоставок на очереди
`services.mail.donstroy.success` до и после выкатки и включить `ack_unmatched` на
той подписке — это тот самый случай, с которого пункт бэклога начался.

**Следующий план.** `warmup-loses-the-message-invisibly` правит те же функции.
Измеренные на брокере факты, которые относятся к нему: `x-delivery-count` есть
только у quorum-очередей, а `x-delivery-limit` считает доставки, а не перевыдачи —
при `x-delivery-limit=3` сообщение исчезает после четвёртой доставки, то есть
бюджет равен `limit + 1`.
