# Проверка watcher'а на живом стенде

Всё поведение watcher'а при разрывах связи покрыто юнит-тестами на моках и
подтверждено исходниками `aio_pika` 9.6.2 и `aiormq` 6.9.4. Ни один сценарий не
наблюдался на настоящем брокере. Этот документ — то, что закрывает разрыв: набор
сценариев, каждый со способом воспроизведения, ожидаемым поведением и признаком
провала.

Порядок в документе — от главного к частному. Если времени мало, сценарии 1–3 и
10–11 дают ответ на вопрос «работает ли то, ради чего всё делалось».

## Что считается пройденным

Прогон засчитан, когда выполнено всё:

- ни один сценарий не оставил систему в состоянии, из которого она не вышла сама
  после устранения внешней причины, без рестарта контейнеров Airflow;
- страница Subscriptions ни разу не показала `connected` там, где у брокера нет
  нашего consumer'а, и ни разу не показала `error` там, где он есть;
- ни одно сообщение не потеряно и ни одно не привело к двум DAG run'ам;
- за сутки прогона число соединений, каналов и consumer'ов в брокере не растёт,
  а `rmq_watcher.tasks_abandoned` не увеличивается.

## Стенд

### Что нужно

- Airflow со scheduler'ом, в котором поднят плагин, и webserver для страницы
  `/rmq-watcher/subscriptions`. **Одна реплика scheduler'а** — про HA см. раздел
  «Известные ограничения».
- RabbitMQ, к которому есть административный доступ: `rabbitmqctl` или консоль
  контейнера. Кластер из трёх узлов желателен для сценария 6, но не обязателен.
- Airflow Connection типа AMQP с заполненными `login`/`password`/`schema` и
  `management_url` в extra. Учётной записи нужен тег `management`:
  `rabbitmqctl set_user_tags <user> management`.
- Права на `rmq_watcher.*` — нужны для cooldown и exchange-режима:
  ```
  rabbitmqctl set_permissions -p <vhost> <user> \
    "^(rmq_watcher\..*|test\..*)$" "^(rmq_watcher\..*|test\..*)$" "^(rmq_watcher\..*|test\..*)$"
  ```

### Что проверить до начала

Два пункта инфраструктуры, из-за которых сценарии 2 и 3 могут соврать:

- если AMQP идёт через traefik, у его entrypoint должен стоять `readTimeout=0s`
  — иначе прокси сам рвёт долгоживущее соединение по своему таймауту, и
  наблюдаемое поведение будет про прокси, а не про watcher;
- `rabbitmq.conf` должен быть смонтирован в контейнер брокера — иначе
  `consumer_timeout` и пороги resource alarm не те, что вы задаёте.

### Настройки на время прогона

Дефолты рассчитаны на продакшен и делают прогон медленным. На время проверки:

| Что | Куда | Значение | Зачем |
|---|---|---|---|
| `rmq_watcher_reconcile_interval` | Airflow Variable | `20` | цикл раз в 20 с, два негативных вердикта ≈ 40 с вместо 2 минут |
| `heartbeat` | extra подключения | `10` | обрыв становится исключением за ~30 с вместо ~90 с |
| `rpc_timeout` | extra подключения | `10` | зависший вызов виден быстрее |

`rmq_watcher_cycle_timeout` не трогайте: он и так `max(interval × 3, 300)`, то
есть 300 с, и сценарий 9 проверяет именно этот бюджет.

Обе Variables перечитываются в начале каждого цикла — менять их можно на ходу,
рестарт не нужен. Значения из extra подключения применяются на следующем
подключении.

### Где смотреть

Четыре окна наблюдения, все нужны одновременно:

1. **Страница Subscriptions** — блок Connections (строка на `conn_id`: Status,
   Consumers, Broker consumers, Last reconcile, Last Error) и таблица подписок
   ниже (собственный статус каждой).
2. **Логи scheduler'а** — `grep -E 'rmq_watcher|RMQ Watcher|consumer|liveness'`.
3. **Брокер** — что он думает на самом деле:
   ```
   rabbitmqctl list_consumers -p <vhost>
   rabbitmqctl list_queues -p <vhost> name messages consumers
   rabbitmqctl list_connections name state user
   rabbitmqctl list_channels connection number consumer_count
   ```
4. **Метрики statsd**, если подключён: `rmq_watcher.consumer_attached`,
   `consumer_restarted`, `dag_triggered`, `cycle_timed_out`,
   `cycle_step_timed_out`, `cycle_step_skipped`, `tasks_abandoned`.

Главный приём всей проверки: **сравнивать окно 1 с окном 3**. Расхождение между
тем, что показывает страница, и тем, что отвечает `rabbitmqctl list_consumers`, —
это и есть отказ, ради устранения которого написана ветка.

## Подготовка

Заведите три DAG'а — по одному на режим:

```python
@rmq_trigger(queue="test.immediate")           # сценарии 1–9, 10
@rmq_trigger(queue="test.cooldown", cooldown=120)  # сценарий 11
@rmq_trigger(exchange="test.events", routing_keys=["a.#"])  # сценарий 12
```

Очереди `test.immediate` и `test.cooldown` создайте руками (queue-режим читает
их `passive`-declare'ом и не создаёт). Для сценариев с quorum-очередью объявите
их `x-queue-type=quorum` — так проверяется и расход delivery-limit.

**Базовое состояние.** Дождитесь, пока в блоке Connections появится строка со
`status=connected`, `Consumers` равным числу подписок (плюс единица, если есть
cooldown — fire-консьюмер), `Broker consumers` равным тому же числу и свежим
Last reconcile. Убедитесь, что `rabbitmqctl list_consumers` показывает столько
же тегов вида `rmq_watcher.{hostname}.{pid}.{sub_id}.{nonce}`. Пока эти два
числа не сошлись, начинать сценарии бессмысленно.

Отправка тестового сообщения:
```
rabbitmqadmin publish routing_key=test.immediate payload='{"n":1}' properties='{"message_id":"m-1"}'
```

## Сценарий 1. Рестарт брокера

**Что имитируем.** Исходный инцидент: RabbitMQ перезапускается, consumer'ов на
очередях не остаётся, клиентское соединение остаётся объектом без транспорта.

**Как.** `docker restart rabbitmq` (или `systemctl restart rabbitmq-server`).

**Ожидаемо.**

1. В течение одного-двух циклов (≈ 20–40 с при интервале 20) строка `conn_id`
   уходит в `error`, Last Error называет причину и номер проверки
   (`negative check 1 of 2`). Подписки показывают `error` или `connecting`.
2. После второй отрицательной проверки соединение пересоздаётся, в логе —
   `Restarting consumer of subscription N`, `consumer_restarted` растёт.
3. Ещё через цикл строка возвращается в `connected`, `Broker consumers` снова
   равен `Consumers`, `rabbitmqctl list_consumers` показывает новые теги — с
   **другим** `nonce` в конце.
4. Сообщение, отправленное сразу после восстановления, запускает DAG.

**Провал.** Строка осталась `connected` в момент, когда `list_consumers` пуст.
Или не вернулась в `connected` за 5 циклов. Или потребовался рестарт scheduler'а.

**Время.** До 3 минут.

## Сценарий 2. Зомби-соединение — главный сценарий

**Что имитируем.** Связь оборвана так, что TCP-сокет остаётся открытым с нашей
стороны: клиент считает соединение живым, брокер о нём уже не знает. Это
отличается от сценария 1 тем, что клиент не получает ни FIN, ни RST — и именно
на этом отказе UI показывал `connected` больше суток.

**Как.** Со стороны хоста Airflow молча отбрасывать пакеты к брокеру:

```
iptables -I OUTPUT -p tcp --dport 5672 -j DROP
```

Держать 3–5 минут, затем `iptables -D OUTPUT -p tcp --dport 5672 -j DROP`.

**Ожидаемо.**

1. Первые секунды всё выглядит здоровым — это нормально, обрыв ещё некому
   заметить.
2. Через ~3 × heartbeat (≈ 30 с при heartbeat 10) `aiormq` поднимает ошибку,
   либо проба живости не получает ответа за `rpc_timeout`. Строка уходит в
   `error` с причиной вида `passive declare of ... failed`.
3. Пока правило висит, watcher продолжает пытаться: логи показывают циклы
   переподключения, страница держит `error`, `Consumers` может падать до нуля.
4. **Цикл не умирает и бюджет не выбирается**: `cycle_timed_out` не растёт.
5. После снятия правила восстановление идёт само, за один-два цикла, без
   рестарта контейнеров.

**Провал.** Страница показывает `connected` в любой момент, пока правило висит.
Или после снятия правила соединение остаётся нерабочим (в логе повторяется
`Connection was not opened` или таска бесконечно падает на одном и том же
объекте). Или `cycle_timed_out` растёт.

**Время.** 10 минут.

## Сценарий 3. Рестарт прокси

**Что имитируем.** Между Airflow и брокером стоит traefik/haproxy, и он
перезапускается или разрывает соединение по своему таймауту.

**Как.** `docker restart traefik`.

**Ожидаемо.** То же, что в сценарии 2, но обрыв замечается быстрее — прокси
обычно закрывает сокет корректно. Восстановление за один-два цикла.

**Провал.** Соединение восстановилось, а consumer'ы — нет: `list_consumers`
пуст, а страница зелёная. Или в брокере остались висеть старые соединения от
прежнего прокси (проверить `list_connections` — их число не должно расти от
рестарта к рестарту).

**Время.** 5 минут, стоит повторить трижды подряд.

## Сценарий 4. Брокер сам отменяет consumer'а

**Что имитируем.** RabbitMQ шлёт `basic.cancel`, не закрывая ни соединения, ни
канала: удалили очередь, сменился лидер quorum-очереди, перезапустился узел с
classic-очередью. Проба соединения при этом продолжает проходить успешно —
consumer'а уже нет, а соединение живо.

**Как.** Удалить очередь под работающим consumer'ом:
```
rabbitmqctl delete_queue test.immediate -p <vhost>
```

**Ожидаемо.**

1. Watcher замечает отмену по собственному каналу, не спрашивая брокер: тег
   пропал из карты consumer'ов канала. Подписка уходит в `error`, `conn_id` —
   тоже, Last Error называет отменённого consumer'а.
2. Соседние подписки того же `conn_id` **остаются `listening`** и не
   перезапускаются: они здоровы, и общее соединение живо.
3. Пока очереди нет, подписка пишет `error` раз в цикл — это ожидаемо: очередь
   в queue-режиме создаёт оператор, а не провайдер.
4. После того как очередь создадут заново
   (`rabbitmqadmin declare queue name=test.immediate durable=true`), подписка
   возвращается в `listening` на ближайшем цикле.

**Провал.** Страница держит `listening` по удалённой очереди. Или здоровые
соседи получили `error` и были перезапущены — тогда одна удалённая очередь
роняет всё соединение.

**Время.** 5 минут.

## Сценарий 5. Смена лидера quorum-очереди

**Что имитируем.** То же, что 4, но без участия оператора — так это происходит в
кластере само.

**Как.** На кластере из трёх узлов: объявить `test.immediate` как quorum,
дождаться `listening`, затем остановить узел, который держит лидерство
(`rabbitmqctl -n rabbit@nodeX stop_app`).

**Ожидаемо.** Consumer перерегистрируется автоматически либо отменяется и
восстанавливается watcher'ом за один-два цикла. Сообщения, отправленные во время
смены лидера, не теряются.

**Провал.** Подписка осталась `listening`, а `list_consumers` её тега не
показывает. Или сообщения, отправленные в переходный момент, не привели к DAG
run'ам и не остались в очереди.

**Время.** 15 минут. Пропустить, если кластера нет — на одиночном узле сценарий
не воспроизводится.

## Сценарий 6. Resource alarm

**Что имитируем.** У брокера кончается память или диск, он блокирует
публикующие соединения, перестав читать из их сокетов.

**Как.**
```
rabbitmqctl set_vm_memory_high_watermark 0.0001
```
Подержать 2–3 минуты, затем вернуть: `rabbitmqctl set_vm_memory_high_watermark 0.4`.

**Ожидаемо.**

1. Потребление **не останавливается**: publish и consume идут по разным
   соединениям, и заблокировано только публикующее. Подписки без cooldown
   продолжают запускать DAG'и.
2. Cooldown-подписка не может опубликовать placeholder: в логе
   `Publishing the cooldown placeholder ... failed`, доставка возвращается в
   очередь, пауза растёт 1 → 2 → 4 … до 60 с. Строка подписки — `error`.
3. **Строка `conn_id` не становится `error` из-за publish-отказа**: отказ
   публикующей роли не перезаписывает вердикт о потребляющем соединении.
4. После снятия alarm'а всё восстанавливается само, cooldown-окно открывается.

**Провал.** Потребление встало на подписках без cooldown. Или строка `conn_id`
показала `error` с нулём consumer'ов, пока consumer'ы работали. Или
cooldown-доставка переотправлялась чаще раза в секунду (на quorum-очереди это
выжигает delivery-limit).

**Время.** 10 минут.

## Сценарий 7. Management API недоступен

**Что имитируем.** Неверный `management_url`, учётка без тега `management`, 404
или таймаут.

**Как.** Снять тег: `rabbitmqctl set_user_tags <user> ""`. Вернуть через 3–4
цикла: `rabbitmqctl set_user_tags <user> management`.

**Ожидаемо.**

1. Первый неудачный цикл — «нет данных»: WARNING в логе, счётчики не тронуты,
   строка сохраняет и статус, и текст Last Error.
2. На **второй** неудаче подряд проверка переходит на passive declare. Колонка
   `Broker consumers` становится `—` (passive declare числа не возвращает), а
   статус остаётся `connected`, потому что соединение отвечает.
3. Watchdog продолжает работать: если в этот момент удалить очередь (сценарий
   4), отмена всё равно будет замечена по каналу.
4. После возврата тега `Broker consumers` снова показывает число.

**Провал.** Все подписки покраснели из-за недоступности API. Или watchdog замолк
совсем: удаление очереди при недоступном API не привело к `error`.

**Время.** 5 минут.

## Сценарий 8. Метабаза Airflow недоступна

**Что имитируем.** Postgres Airflow перестал отвечать, а брокер жив.

**Как.** `docker pause airflow-postgres` на 60–90 с, затем `docker unpause`.
(Пауза, а не остановка: нужен именно неотвечающий сокет, а не отказ в
соединении.)

**Ожидаемо.**

1. Цикл не зависает: каждый блокирующий шаг ограничен своими 60 с, чтение
   подключения — 30 с. В логе — `cycle_step_timed_out` или `cycle_step_skipped`.
2. Consumer-задачи продолжают потреблять; DAG'и, разумеется, не запускаются —
   `trigger_dag` тоже идёт в метабазу, доставка возвращается в очередь с растущей
   паузой.
3. Пулы потоков не забиваются: `cycle_step_skipped` может расти, но watcher
   после `unpause` возвращается к работе сам.
4. Сообщения, пришедшие во время паузы, запускают DAG'и после восстановления.

**Провал.** Watcher не восстановился после `unpause`. Или сообщения потеряны. Или
`cycle_timed_out` растёт непрерывно (значит, шаг не уложился в собственный
бюджет и съел общий).

**Время.** 10 минут.

## Сценарий 9. Немедленный режим: at-least-once и дедупликация

**Что имитируем.** Обычную работу и падение запуска DAG'а.

**Как.**

1. Опубликовать сообщение с `message_id=m-1` → DAG запускается, run_id
   `rmq__test.immediate__m-1`.
2. Опубликовать **то же** `message_id=m-1` ещё раз → второго run'а быть не
   должно, сообщение подтверждается как дубль.
3. Опубликовать без `message_id` дважды → должно быть два run'а (дедупликация
   опирается на продюсера).
4. Поставить DAG на паузу и опубликовать сообщение → run'а нет, сообщение
   подтверждено и отброшено намеренно, в логе сказано почему.
5. Уронить запуск: временно снять права на метабазу или удалить DAG-файл при
   существующей подписке → доставка возвращается в очередь, статус `error`,
   пауза растёт 1 → 60 с; после починки run создаётся.

**Провал.** Сообщение подтверждено раньше, чем создан run (проверяется тем, что
после падения на шаге 5 сообщение осталось в очереди). Или два разных сообщения
схлопнулись в один run.

**Время.** 15 минут.

## Сценарий 10. Cooldown полностью

**Что имитируем.** Подавление всплеска: первое сообщение открывает окно, DAG
запускается по его истечении, всё внутри окна отбрасывается.

Это **первый настоящий прогон** механизма: до правки в этой ветке placeholder
не доходил до брокера ни разу.

**Как.** Подписка с `cooldown=120`.

1. Убедиться, что инфраструктура объявлена: `rmq_watcher.fire` (exchange и
   очередь), `rmq_watcher.pending.{dag_id}` с `x-max-length=1`,
   `x-overflow=reject-publish`, `x-dead-letter-exchange=rmq_watcher.fire`,
   `x-dead-letter-routing-key={dag_id}`:
   ```
   rabbitmqctl list_queues -p <vhost> name arguments messages
   ```
2. Опубликовать сообщение в `test.cooldown`.
3. Сразу проверить, что в `rmq_watcher.pending.{dag_id}` **лежит одно
   сообщение** — это и есть placeholder с TTL 120 с.
4. Опубликовать ещё три сообщения подряд → все подтверждены и отброшены, в
   логе INFO про отклонённый placeholder, в pending по-прежнему одно.
5. Подождать 120 с → placeholder истекает, уходит по DLX в `rmq_watcher.fire`,
   fire-консьюмер запускает DAG с run_id `rmq_cooldown__{dag_id}__{message_id}`.
6. Опубликовать ещё одно сообщение → окно открывается заново.

**Провал.** Пункт 3 показал пустую pending-очередь — значит placeholder не
доходит до брокера, и весь механизм мёртв. Или на шаге 5 DAG не запустился. Или
на шаге 4 сообщения возвращались в очередь вместо подтверждения (на quorum-
очереди это видно по растущему счётчику доставок).

**Время.** 15 минут.

## Сценарий 11. Exchange-режим

**Как.**

1. Убедиться, что провайдер объявил: exchange `test.events` (topic, durable,
   `alternate-exchange=test.events.unrouted`), очереди `test.events.unrouted` и
   `test.events.log` с TTL 8 ч, очередь `rmq_watcher.sub.{dag_id}` с TTL 8 ч и
   биндингом по `a.#`.
2. Публикация с ключом `a.b` → DAG запускается, копия падает в `.log`.
3. Публикация с ключом `z.z` → DAG не запускается, сообщение падает в
   `.unrouted`.
4. Поменять `routing_keys` в DAG-файле на `["b.#"]` → на ближайшем цикле
   биндинг `a.#` снимается, `b.#` добавляется. Проверить в Management UI.
5. Удалить биндинг руками → следующий цикл его восстанавливает.

**Провал.** Биндинги не сходятся с декоратором после цикла. Или сообщение по
снятому ключу продолжает запускать DAG.

**Время.** 15 минут.

---

## Сценарий 12. Остановка и рестарт scheduler'а

**Что имитируем.** Штатный рестарт: consumer'ы должны сняться, а не остаться
призраками, за которых потом поручится проверка живости.

**Как.** `docker restart airflow-scheduler`, затем сразу
`rabbitmqctl list_consumers -p <vhost>`.

**Ожидаемо.**

1. Перед остановкой подписки получают статус `disconnected` — он дописывается
   до закрытия соединений.
2. После рестарта в брокере ровно столько consumer'ов, сколько подписок, и все
   с новым `pid` в теге. Старых тегов нет.
3. Строки `conn_id` не остаются в `error` навсегда.

**Провал.** В `list_consumers` видны теги с прежним `pid` — брокер держит
призраков. Или число consumer'ов от рестарта к рестарту растёт.

**Время.** 5 минут, повторить трижды.

### Сценарий 12а. Прогрев DAG-процессора

**Что проверяем.** Что сообщение, дожидающееся ещё не разобранного DAG'а, не
красит строку подписки.

**Как.**

1. Остановить scheduler: `docker stop airflow-scheduler`.
2. Положить в очередь подходящее сообщение — оно пролежит там до подъёма.
3. Поднять scheduler: `docker start airflow-scheduler`.
4. Смотреть страницу подписок и `docker logs -f airflow-scheduler` с первой
   секунды: разбор DAG-файлов занимает минуты, и окно прогрева видно только в
   этот промежуток.

**Ожидаемо.**

1. Строка подписки идёт `connecting` → `listening` и в `listening` остаётся.
   `error` не появляется ни разу.
2. В логе — строка про DAG, у которого ещё нет сериализованной версии, с
   номером доставки подряд и паузой до следующей попытки. Идёт она INFO, а
   каждая десятая — WARNING'ом.
3. Строка `conn_id` держится `connected`: подписка остаётся кандидатом проверки
   живости, и брокер подтверждает её тег.
4. Как только DAG-процессор разобрал файл, сообщение запускает DAG run и
   подтверждается. Строка остаётся `listening`.

**Провал.** Строка подписки или строка `conn_id` получила `error`, пока в логе
идут сообщения про несериализованный DAG и их номер не дошёл до 25: после
двадцать пятой доставки подряд `error` — это спроектированный исход, а не
провал. Или сообщение так и не запустило DAG после разбора файлов.

**Время.** 10 минут.

### Сценарий 12б. Страница подписок у роли Op

**Что проверяем.** Что провайдер открывает страницу роли Op на старте
веб-сервера и закрывает её по переключателю.

**Как.**

1. Завести пользователя с единственной ролью `Op` и зайти под ним.
2. Перезапустить веб-сервер: `docker restart airflow-webserver`.
3. Открыть меню `RabbitMQ` → `Subscriptions`.
4. Поставить `airflow variables set rmq_watcher_grant_op_access false` и
   перезапустить веб-сервер ещё раз.

**Ожидаемо.**

1. После первого перезапуска пункт меню виден, страница открывается, кнопки
   создания и удаления работают.
2. В логе веб-сервера — строка про выданные права страницы роли Op.
3. После второго перезапуска пункта меню нет, а прямой заход на
   `/rmq-watcher/subscriptions` отвечает отказом.

**Провал.** Пункт меню не появился после старта на чистой метабазе более одного
раза подряд (первый старт роли `Op` ещё не видит — это ожидаемо и написано в
readme). Или ложное значение переменной страницу не закрыло.

**Время.** 10 минут.

## Сценарий 13. Изменение подписок на ходу

**Как.**

1. Выключить подписку в UI → её consumer снимается, строка получает
   `disconnected`, тег исчезает из `list_consumers`.
2. Включить обратно → consumer появляется, статус `listening`.
3. Удалить `@rmq_trigger` из DAG-файла → подписка исчезает из списка, а её
   consumer снимается с брокера.
4. Изменить `cooldown` у подписки → применяется на следующем цикле.

**Провал.** Тег выключенной подписки остался в `list_consumers`. Или строка
удалённой подписки навсегда осталась в `listening`.

**Время.** 10 минут.

## Сценарий 14. Флаг устаревшего цикла

**Что проверяем.** Что бейдж «Last reconcile» зажигается, когда должен, и не
зажигается, когда цикл просто идёт дольше обычного.

**Как.**

1. При работающем watcher'е и интервале 20 с бейдж не должен появляться никогда:
   порог — интервал плюс полный бюджет цикла, то есть 320 с.
2. Остановить scheduler → через ~320 с строка помечается предупреждением.
3. Выключить **все** подписки одного `conn_id` в UI → его строка перестаёт
   штамповаться и через 320 с помечается тоже. Это ожидаемое поведение,
   описанное в readme: строки не удаляются.

**Провал.** Бейдж горит при здоровом работающем цикле.

**Время.** 15 минут.

## Сценарий 15. Длительный прогон

**Как.** Оставить стенд под нагрузкой на 24–48 часов: поток сообщений в
`test.immediate` (хотя бы раз в минуту), периодические рестарты брокера раз в
несколько часов.

**Что смотреть на выходе.**

- `rabbitmqctl list_connections | wc -l` и `list_channels | wc -l` — не растут;
- `rmq_watcher.tasks_abandoned` — не растёт (рост означает, что отменённые
  задачи не завершаются, то есть соединение не отвечает вовсе);
- потребление памяти процессом scheduler'а — стабильно;
- в таблице `rmq_watcher_conn_status` `last_reconcile_at` двигается непрерывно;
- ни одного `cycle_timed_out`.

**Провал.** Любой из счётчиков растёт монотонно.

## Известные ограничения — проверять не нужно, знать нужно

- **Несколько реплик scheduler'а.** Кеш «что уже записано в строку» живёт в
  памяти процесса, поэтому одна реплика может держать чужой `error` на здоровой
  подписке до собственной смены статуса. Записано в
  `docs/backlog/status-cache-stale-across-replicas.md`; требует
  лидер-лока или версионирования строки. Прогон ведите на одной реплике.
- **`prefetch` намеренно не выставлен.** Промахи фильтра возвращаются в очередь
  и при конечном окне prefetch забили бы его целиком, остановив потребление.
  Цена — неограниченное число неподтверждённых доставок: при большом бэклоге
  очередь вычитывается в память scheduler'а, а самая старая доставка может
  упереться в `consumer_timeout` брокера (по умолчанию 30 минут). Если на стенде
  ожидается большой бэклог, поднимите `consumer_timeout` в `rabbitmq.conf`.
- **Смена exchange в декораторе** не снимает биндинги прежнего exchange — они
  продолжают доводить сообщения до очереди
  (`docs/backlog/exchange-change-leaves-old-bindings.md`).
- **Аргумент декоратора, который не разбирается статически** (импортированная
  константа, f-строка, вызов), молча теряется
  (`docs/backlog/rmq-trigger-kwargs-silently-dropped.md`).
- **Сообщение, исчерпавшее `delivery-limit` во время прогрева**, пропадает
  незаметно: строка весь прогрев показывает `listening`, а счётчик до порога не
  доходит — двигать его уже нечему
  (`docs/backlog/warmup-loses-the-message-invisibly.md`).
- **Cooldown-DAG, который не сериализуется никогда**, виден только в логе:
  строки у fire-консьюмера нет, порога на этом пути тоже нет
  (`docs/backlog/cooldown-dag-never-serialized-invisible.md`).

## Что записать по итогам

По каждому сценарию: пройден/не пройден, фактическое время до `error` и до
возврата в `connected`, расхождения между страницей и `list_consumers`, если
были. Не пройденные сценарии — с логом scheduler'а за окно отказа и выводом

## Справочник

### Пороги и таймауты

| Что | Значение | Где |
|---|---|---|
| Интервал reconcile | 60 с | Variable `rmq_watcher_reconcile_interval` |
| Бюджет цикла | `max(интервал × 3, 300)` с | Variable `rmq_watcher_cycle_timeout` |
| Отрицательных проверок до перезапуска | 2 | `_NEGATIVE_CHECKS_BEFORE_RESTART` |
| Не чаще одного пересоздания соединения | раз в 5 циклов | `_CYCLES_BEFORE_REDROP` |
| Отказов Management API до passive declare | 2 | `_PROBE_FAILURES_BEFORE_FALLBACK` |
| Циклов без `listening` до опроса соединения | 2 | `_STUCK_CYCLES_BEFORE_DROP` |
| Доставок подряд про несериализованный DAG до `error` | 25 (≈19 минут пауз) | `_NOT_READY_LIMIT` |
| Пауза перед повторным подключением | 5 с | `_RECONNECT_DELAY` |
| Backoff публикации и запуска DAG | 1 → 60 с | `_PUBLISH_BACKOFF_*`, `_TRIGGER_BACKOFF_*` |
| Таймаут HTTP к Management API | 5 с | `_MGMT_HTTP_TIMEOUT` |
| Таймаут вызова к метабазе | 30 с | `_DB_TIMEOUT` |
| Таймаут блокирующего шага цикла | 60 с | `_STEP_TIMEOUT` |
| TTL служебных очередей exchange-режима | 8 ч | `_EXCHANGE_TTL_MS` |
| heartbeat / connect / rpc | 30 / 15 / 30 с | extra подключения |

### Статусы

- Подписка: `connecting`, `listening`, `error`, `disconnected`.
- Соединение: `connected`, `error`, `degraded` (отрицательный вердикт задержан
  ограничителем пересозданий), `unknown` (вердикта не было ни разу).

### Объекты в брокере

| Имя | Что это |
|---|---|
| `rmq_watcher.{host}.{pid}.{sub_id}.{nonce}` | consumer-тег подписки |
| `rmq_watcher.{host}.{pid}.fire.{nonce}` | consumer-тег fire-консьюмера |
| `rmq_watcher.pending.{dag_id}` | окно cooldown: одно сообщение с TTL |
| `rmq_watcher.fire` | exchange и очередь истёкших окон |
| `rmq_watcher.sub.{dag_id}` | очередь exchange-режима |
| `{exchange}.unrouted`, `{exchange}.log` | страховочные очереди exchange-режима |

### Идентификаторы DAG run'ов

- немедленный режим: `rmq__{queue_name}__{message_id}`;
- cooldown: `rmq_cooldown__{dag_id}__{message_id}`.

Значение длиннее 250 символов или с недопустимыми символами усекается и получает
32-символьный дайджест — по нему и различаются такие run'ы.
